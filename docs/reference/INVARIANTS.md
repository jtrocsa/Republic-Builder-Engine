# Chronicle invariants and terminology — the long form

**This is the reference copy. The short, binding version is in `CLAUDE.md`.**

Both sections below were moved here verbatim from `CLAUDE.md` in the Phase 90 workflow audit. Nothing
was cut in the move; `CLAUDE.md` now carries the rule for each entry in one or two lines and points
here for the rest.

The reason for the split is cost. `CLAUDE.md` is loaded in full at the start of every session and
inherited by every subagent, and these two sections were 55% of an 83 KB file — roughly 11,000 tokens
paid up front, every time, most of it incident history rather than instruction. The rules are worth
that; the stories behind them are worth reading once, when you are working in that area.

**A rule here is as binding as a rule in `CLAUDE.md`.** Read the entry in full before changing code
in its area — the narrative is usually a record of the same bug shipping twice, and it is the part
that tells you which fix is the wrong one.

---

## Terminology

Use these consistently in code, copy, and UI strings — they're the game's fixed internal vocabulary:

- **Chronicle Institute** — the organization; **Institute Archive** — the visible hub room/screen name (`chrome()`'s "Institute" branding + `HUB_TARGETS`/`institute` screen in `main.js`).
- **Entrance Hall** — the room the player arrives in and the first thing they control (Phase 63, decision log `0046`). One of **three** hub rooms, all on the `institute` screen and told apart by `progress.currentHubRoom` (`"main"` | `"archive"` | `"hallway"`), resolved through `activeHubGrid()`/`activeHubBlocks()`/`activeHubTargets()`/`activeHubNpcRuntime()`. There is no `intro-hallway` screen any more — it was retired along with the five-second scripted float that used to live on it; don't reintroduce a screen for a room. `hallway.tmj` is that room; `institute-hall.tmj` is the Main Hall.
- **Chronotravel** — traveling to a historical setting (the `travel` screen / "Initiate Chronotravel"). **Only a case with a map travels** (`0114`): the other two cases in every unit open straight onto their own screen, and the Navigation Table's button has said so since Phase 59 — it reads "Open <mission name>" for those and "Initiate Chronotravel" only for the one that walks.
- **Chronotravel plate** — the painted establishing shot a warp screen loads on, one per destination (`content/chronotravel-plates.js`, art in `assets/plates/`). **Keyed by unit, and exactly one case per unit opens on it** — the one that walks that unit's map (`route: "field"`). The plate is the unit's map painted from outside, which is true of a _unit_ only through its map: this entry used to read "a unit is one place and one era, so Unit 1's three cases all open on it whether they route to a field map or not", and on the other sixteen cases that put a Kansas railhead behind "Chicago, Illinois · 1893" and a 1957 boulevard behind "The United States Senate · 1 June 1950". **A case with no map does not open a warp at all** (`0114`). Everything else on the card comes from the case and the unit, so a renamed mission renames its own loading screen. A plate's `note` is **flavour and must stay flavour** — it is the one screen with a player's whole attention and no task on it, which is the reason to refuse the temptation to teach through it. Units 7–9's plates were painted and committed **unwired**, so a new unit was one table line — Unit 7 collected its line in Phase 89, Unit 8 in Phase 95 and Unit 9 in Phase 100, and **the queue has been empty since**. `tests/unit/chronotravel-plates.test.js` fails if a shipped unit has no plate, if the table names a unit that does not exist, if the directory and the table stop agreeing exactly, or if a unit's `route: "field"` case count is anything but one — every guard there reads the _table_, which is why none of them could see `0114`'s defect, and the last one is the one that now can. Build them with `npm run assets:build-plates` — sources live in a gitignored `art-source/plates/`, out of `assets/` so nothing can reference the 2.5 MB PNG by accident.
- **Warp screen** — the two transitions, built by one function (`warpScreen()` in `main.js`, Phase 88A/88B, decision logs `0073` and `0074`): `travel` out and `return-warp` back, differing only in which plate they load, which way the streaks and anchor rings run, and three strings. Full-bleed and **chrome-less**, like the title sequence. **Two beats and three phases on one render**, flipped on `data-warp-phase` by `beginWarp()`: `tunnel` (a canvas streak field over `WARP_TUNNEL_MS`, its own bottom bar, the destination card resolving out of blur), `plate` (the painting settles, a ring fills 0%→100% over `WARP_DWELL_MS`) and `ready` (the ring reads "Synced" and the arrival prompt appears). All three phases are emitted once and CSS decides what shows — a phase flip never rebuilds markup, which would restart the plate's own settle — and everything in the second beat is **delayed by `--warp-tunnel` rather than started by the flip**, because a CSS delay is exact and a class swap is a frame or two late. **The loading is real**: the dwell is a floor and the destination's art is a gate, so `SURFACE_TILESETS` warms the arrival surface's tilesets — they are eagerly globbed _URLs_, not bytes, which is why a first visit to a map used to open on an empty frame. Three guards exist because a stuck loading screen is worse than anything they protect against: `WARP_ASSET_CEILING_MS`, a swallowed throw in `tilesetsFor()`, and the `warpRun` token that `render()` bumps (a promise chain has nothing to clear, unlike the `setTimeout` it replaced). **The ring shows the dwell, not the bytes** — a JS bar reading real load state was written and thrown away for making the visual baseline a coin toss, so the sweep is CSS over `--warp-dwell` and the number is an animated `@property --warp-pct` read through a counter, which **must declare `inherits: true`** or the `::after` that draws it reads the initial value and sits on 0%. **The tunnel is the one looping thing here and `warpScreen()` does not emit its canvas at all under `prefers-reduced-motion: reduce`** — the phase starts at `plate`, which is both the right behaviour and what keeps the baselines deterministic, since they are captured in exactly that media state. **The screen no longer leaves on its own**: `warp-enter` and `skip-warp` both route through `leaveWarp()`, the skip is live throughout and the prompt once both gates open, and nothing times out behind a player who walks away. **Both recall paths play it**, including the field beacon, which cut straight to the hall until Phase 88A. **Only a `route: "field"` case opens the outbound one** (`0114`); `warpArtUrls()`'s non-field branch is kept for a save resumed mid-warp, and there is a test for that path.
- **Preservation Case** — the badge-case UI opened from the Archive trophy shelf (`unitOneBadgeCaseMarkup()` in `main.js`), styled like a Pokémon badge case, not a debug panel.
- **Navigation Table** — the physical Archive object the player walks to and interacts with to pick a case/route (`archive` screen, `HUB_TARGETS.table`).
- **Recall to Archive** — the field control that returns the player to the Institute. Since Phase 58 it lands the player beside the Navigation Table, not at the Archive Room door. **Two buttons, one action** as of Phase 90D: the in-world beacon and the field screen's back link both carry `field-recall`, both play the return warp, and both say the same three words. The back link used to run `home` — instant cut, no notice, foyer spawn — which is why the beacon's spec now scopes to `.recall-beacon` rather than the bare action. Anything that repoints this control must carry the `exitPreviewIfActive()` guard with it; it is one of the two documented ways a teacher leaves a content preview. **Two buttons, one action — and only one of them has a position.** As of Phase 90E the beacon is proximity-gated like every other world marker (`isNearRecallBeacon()`, the 1.55 object reach) and reports `is-near`, because a gate the player cannot see reads as a dead button; the back link is not gated and must never be, since it has no place in the world and gating it would strand a player in a corner. That is exactly why the gate scopes to `.recall-beacon` and not to the action. The beacon stays **out of `nearestFieldInteraction()`** deliberately, so `E` never offers it: three of the seven maps walk a body inside its reach (0.92, 0.10 and 1.68 tiles), and a fourth competitor in a nearest-wins sort would cost those maps an NPC to reach a control already one Tab away.
- **Mission Tracker** — the field's objective panel, pinned inside `.field-viewport` and outside `.caribbean-world` (`fieldObjectiveTracker()` in `main.js`). Called "Records to Recover" from Phase 57 until Phase 69, when it was renamed and gained a second block for the mission in flight. It is **one block** again as of Phase 71: the record row for the mission you have open takes that mission's own name, and the progress line, its CSS bar and the notebook button follow the list. A record you have _not_ opened still names the person carrying it, because that is what a player can spot across the map — the swap happens when you have it. Don't reintroduce a name heading under the list; that is the duplication Phase 71 removed. A TRACE declares no `summary()`, so it gets a row and a button and no line or bar, which is correct rather than a gap to fill.
- **Activity engine** — a playable interaction hosted on the `activity` screen, defined in `apps/web/src/engine/activities/` (Phase 68, decision log `0051`). Four exist: `interview`, `assembly`, `discrepancy`, `trace`. **The engine key is three things at once** — the registry key, the screen id in `VALID_SCREENS`, and the string a source's `activityRoute` carries — so renaming one is a save-compatibility change, not a refactor. An engine holds **no APUSH facts**; everything a mission says lives in `content/activities/`, and `validate:content` fails if a source's `activityRoute` and its activity's `kind` disagree. Which record is open is `progress.activeActivitySourceId`, not the module-local `openSourceId`. Controls use `data-activity-action`, deliberately not `data-action`. There are **two** optional registry slots. `renderInline` puts an engine's controls in the field dialogue bubble out on the map and **INTERVIEW is still its only implementer**, because it is the only engine that runs part of itself off its own screen. `summary` — the one-line `{ label, done, total }` — is **implemented by all four as of Phase 109** and read by two consumers, the Mission Tracker and the activity screen's own objective line. INTERVIEW was the only implementer until then, so both surfaces were blank on **seventeen of the twenty-four shipped missions**, and the registry comment plus `activity-engines-index.test.js` both asserted that this was correct: the comment argued a TRACE is "a chain, not a count", which is true of what a trace means and beside the point of a player wanting to know how many legs are open — and it named TRACE while ASSEMBLY (slots) and DISCREPANCY (claims) are plainly ratios that were simply never asked. The test now asserts **every** engine rather than a list, so a fifth has to answer the question rather than inherit the omission. Each implementation reuses the per-item status function its own renderer already calls, so no board carries a second opinion about what counts as done. See decision log `0108` §5. **Every authored field map has three missions as of Phase 89E** (decision log `0065`, `0071`, `0081`), and the slates are fixed for all nine units in `docs/design/THE-MAP-PROGRAM.md` §2: Caribbean, Richmond and Ellis Island `interview`/`assembly`/`discrepancy`, Riverbend `interview`/`discrepancy`/`trace`, Philadelphia and Cottonwood Junction `interview`/`assembly`/`trace`, Canal Crossroads `assembly`/`discrepancy`/`trace` — **the one map with no interview**, which is a stated debt paid in companion dialogue rather than a free variety win. **A unit must not repeat its neighbour's three engines, and the question is the half that binds**: with four engines and three slots any two slates share at least one, so an engine that repeats has to be pointed at a different question. The five shipped interviews ask how one arrangement looks from eight positions inside it, what a public position is made of, what testimony costs when the government is writing it down, what entitles a person to be standing here and on whose paper, and what the official question fails to ask. That is `MISSION-ACTIVITY-CATALOG.md` §5 rule 2 as amended in Phase 81A and applied since. **Read the slate off `THE-MAP-PROGRAM.md` §2's own table, never off a prose summary of it** — Unit 7's campaign header shipped in Phase 89 saying slate A was interview/assembly/trace, which is slate C's line, and three later documents copied it before Phase 89E checked; see decision log `0081` §5. The table's "adjacency holds throughout" is the invariant a wrong slate breaks, and nothing in the suite tests it. **An ASSEMBLY slot takes exactly one fragment**, and every slot must be claimed — the schema enforces both, and the reason is that an assembly is a reconstruction with one correct configuration rather than a sort. Unit 6's payroll was first drafted with six charges going into one "charged back" column and returned six schema errors in one shape; the rebuild sorts them by _kind_ of charge instead and is better for it. **Only a field case can host an activity**: the fourteen non-map cases declare no `sources`, and `missionScreen()` has no path into an activity screen. **An activity states its own rules**: `howItWorks`, `terms` and `briefing` are shared optional fields (`COMMON_ACTIVITY_FIELDS` in `contract.js`) — treat all three as authoring defaults, not extras, because the Phase 69 playtest established that a mission which does not explain itself is not playable however good the mechanic is (decision log `0052`). **A wrong choice says something, on every engine** (Phase 110, decision log `0109`). DISCREPANCY and TRACE tinted the pressed button red and printed nothing, then printed 100-200 words of `why` the moment the player was already right — **eleven of the twenty-four missions**, beside an ASSEMBLY that has walked `fragmentNote()`'s hint ladder since Phase 68. Each now prints one line under a choice that missed, and it is **placeless**: it names where to look on that kind of board, which is a fact about the mechanic and not the period, so it lives in the engine and not in eleven content files — the register the default `lockedNote` reached for when it lost the word "island". TRACE carries **two** strings because it asks two questions and a nudge pointed at the wrong one is worse than silence: the ledger axis asks what a step does to the record, the support axis how far the account carries it. Deliberately **not** content-overridable — an optional field would be one `||` away and nothing would author it, which is where `hints` and `supportLevels` have sat since Phase 76. **Right and wrong also sound different**: `handleActivityAction()` fired one cue on every accepted verb and nothing at all on a refused one, so logging the answer that carries the mission and logging one that carries nothing were the same noise. The test is generic because Phase 109 made it so — every engine reports `{ done, total }` and every notebook is `{ kept: [] }`, so **landed = the ratio went up, or an entry was kept, or the record just closed**; the third term is required because no board count moves when the closer lands. `secure` when it lands, the new `flat` cue when it does not, and **a refused press gets `flat` too** — to a player, "refused" and "that gathered nothing" are the same message. **A record that is filed is filed** (Phase 90F/90G, decision logs `0084` and `0085`): once a mission is complete, every engine's reducer refuses every verb that could make it incomplete again, and every renderer disables its own controls. `file` used to overwrite `state.filed` unconditionally the moment a board was settled, so reopening a finished mission from the Mission Tracker — a documented reason to reopen one — and clicking a wrong conclusion un-finished a record `fileToCodex()` **deliberately never unfiles**, leaving the board saying wrong and the archive saying filed. **90F closed the closer and that was one door of five.** Completion is `<board settled> && correct && supported` and both halves stay mutable after filing: `release` drops evidence the conclusion names, `lift` un-solves an assembly, a flipped `verdict` un-settles an audit, and re-logging a leg un-does a trace. All four were live on shipped content. The guard is now the **top of each reducer** — above the `actNotebook` delegation, because that is where `release` is handled — and each `render()` computes the same `isXComplete(activity, state)` from its own module. **Both layers ask the engine's own predicate and nothing is plumbed**: the shared `renderCloser()` still derives it from `!locked && correct && supported` (three values it already holds), while `renderNotebook()` is **told** through `{ settled }`, because it has no `locked` to negate and guessing would lock a legacy save whose board came apart before the guard existed. **INTERVIEW exempts `ask` and `log`** and that exemption is load-bearing: they are the only verbs in the folder that happen off the activity screen — out on the map, where `renderInterviewInline()` draws four chips on a speaker whatever the mission's state — so a blanket freeze leaves dead chips on every stranger; neither can un-complete anything, since both only ever add and coverage counts `logged`. A fifth engine reusing the shared closer inherits the closer's half and must carry the reducer's. Only that exact state closes: a wrong conclusion and a correct-but-unsupported one both stay live, because both are things the player is meant to change. **A Field Notebook `capacity` caps what you keep, not what you gather** (Phase 72), and Ellis Island's interview is the first on that engine to declare one: it asks for all eight useful answers through `requires.useful` and keeps three, and the closer's correct option names two of them through `requiresEvidence` — so the right conclusion filed on the wrong three findings reads as _unsupported_, which is neither a pass nor a buzzer. **All five activities that declare a capacity also declare `requiresEvidence`**, which is why `release` could un-file a finished record until Phase 90G. **The debrief prints what was kept, and only where a capacity made it a choice** (`missionDebriefScreen()`, gated on `activity.notebook`) — from `activityOutcome()`'s own evidence, under the Codex's own "What you kept" heading. The other sixteen keep everything they surface, so there is nothing to reflect back and the section is omitted rather than padded. **`howItWorks` is a screen, not a panel** (Phase 71, decision log `0054`): an activity opens on **Mission Instructions**, the activity screen's own first state — not a fifth screen id — gated on a per-record `briefed` flag beside `state`/`completed` in `progress.sourceActivities`, dismissed by `data-action="mission-briefed"` (a plain `data-action`, because `data-activity-action` is matched first and dispatches into the engine reducer). It opens on the giver's portrait, resolved in three tiers: the activity's `briefing.speaker`, else the record's map anchor, else the engine's mark. **Three steps, capped at four by the schema** — six bullets is a wall nobody reads. **The board's copy of those steps carries the same heading as the screen that gave them** — both say "Mission Instructions" as of Phase 90F; the board said "How this works" from Phase 69 and the screen took its own name in Phase 71, so they disagreed for nineteen phases, and a student looking for what they read thirty seconds ago found something with another name. **That copy is collapsed as of Phase 109** (decision log `0108`), along with the glossary and the briefing, into three `<details>` built by `activityCopySection()`: the column re-printed the whole hand-off screen and left it open for the rest of the mission — **244 words measured in a browser, in a ~348px column with no breakpoint to reflow into** — so the question the mission asks arrived underneath everything already read. Folding is not licence to rename: the `<summary>` still says "Mission Instructions", and its label has its own `<b>` so the spec can keep asserting that exactly. What stays open in their place is the mission's question and **one objective line**, which is why §5's missing summaries had to be written in the same phase — folding the instructions away on a screen that then says nothing about what it is waiting for is a worse screen, not a shorter one. **The open flag lives in `progress.settings.activityCopyOpen`, and that is not optional**: `render()` assigns `app.innerHTML` wholesale, so a native `<details>` here is closed again on every press: `handleActivityCopyToggle()` is a capture-phase listener (`toggle` does not bubble) that saves and **deliberately does not re-render**, since the browser has already opened the panel. **The activity screen states progress in exactly one place** — that objective line. INTERVIEW's own `.activity-progress` row printed the same sentence from the same `interviewSummary()` and is gone; all seven shipped interviews declare a single goal, so it was never more than the one line. **The INTERVIEW board has nothing on it to press, and says so itself** (Phase 90F): the asking happens out on the map through `renderInline`, so a first visit is a blank grid, an empty notebook and a locked closer — four buttons, none of them enabled. `renderInterview()` prints one placeless line until somebody has been asked anything. It belongs in the engine and not in seven content files, because "the questions are put to people out in the field" is a fact about INTERVIEW and not about the Caribbean — the same register the default `lockedNote` reached for when it lost the word "island". Don't re-author it into a step. **In an INTERVIEW, `asked` and `logged` are different lists** — coverage, the notebook, the outcome and `interviewTokens()` all count `logged`, so an answer the player heard and walked away from buys nothing. **`interviewTokens()` walks every unit's interviews and its ids are not unit-scoped** — it emits `asked:<speaker>:<question>`, and question ids are generic (`gold`, `grows`, `decides`), so a reused speaker id would hand a player evidence in one unit's DISCREPANCY that they earned in another. Swept clean at zero collisions in Phase 90F across all seven interviews; **nothing enforces it and nothing tests it**, so check a new interview's speaker ids against the shipped ones. **An INTERVIEW's answer grid is deliberately sparse** (Phase 71): one useful answer, two short deflections, and at least one question per speaker left unauthored so their `fallback` fires — a full grid makes asking everyone everything strictly dominant, and both shipped interviews had one until Phase 71, which left all fifteen authored `fallback` lines permanently unreachable. A fallback offers **no log control** and `actInterview` refuses the verb for one; it is a stage direction, not testimony. **A deflection is loggable, and the receipt says what logging it got you** (Phase 106, decision log `0105`): `log` has three outcomes — a flat answer written into the grid and nowhere else, a useful answer on a rationed notebook that is only _available_ in the panel until a second press keeps it, and a useful answer with no capacity, which really is in the Field Notebook — and `interviewLogReceipt()` is the one place they are told apart. Until Phase 106 the control claimed the third for all three, on **104 of the 156 authored answers in the game** and on the first interaction of the first mission; on Units 7 and 8, which ration, it was false for every answer. **The offer stays one string under every authored answer**, deliberately — which answers carry something is what an interview is for, and a button that changed its words would give it away before the press. Only the receipt differs, and only after the player has committed. **Each receipt carries its own mark, and the three are the game's own three** (Phase 110, decision log `0109`): `✓` secured, `✦` available and waiting on a second press, `·` nothing here — the set the Mission Tracker's legend teaches on every field map and the world markers and head badges already use. All three printed `✓` until then, so the mark said _secured_ on the 104 answers of 156 that carry nothing, which is the half of P0-3 the words were fixed for and the glyph was not. `.is-candidate` and `.is-kept` also both fell through to the green base rule, so the three receipts rendered as two on the only two interviews that ration. **There is no `✗` anywhere in the game and there should not be** — a deflection is a legal move returning honest nothing, not a wrong answer, and `CHRONICLE-VOCABULARY.md` §2 makes that a pedagogy rule rather than a wording one. **The receipt is one line and that is a budget**, not a preference: it shares its slot with the offer in a bubble already at the limit of what fits above a speaker, so a wrapping receipt grows the bubble on the press. The rationed string's first draft was two lines and `activity-engines.spec.js` measured it; the assertion compares the receipt against the longest of the three strings and against **one computed line height** rather than the offer exactly, because a `<p>` and a `<button>` carrying identical rules land 1.6px apart and always have. `tests/unit/activity-content.test.js` fails on a dense grid, a flat answer over 40 words, or a `briefing` naming somebody who is not on that unit's map. **"That unit's map" means every surface of it, indoors and out** — `fieldNpcById()` has always resolved across `fieldSurfaces()`, so an interior NPC is a legal speaker, briefer and debriefer; the test read the outdoor roster alone until Phase 87 and was rejecting content the game plays correctly. Unit 6's interview names two people in the land office, one of whom is carrying the record it opens from. **`.activity-shell` and `.activity-board` are shared with the practice check, Archive Challenges and non-map missions** — scope any new rule on them with `.activity-shell[data-activity-source]`, or you will re-lay every quest list in the game.
- **Mission** vs. **Archive Challenge** — two distinct groups since Phase 58, and the distinction is load-bearing (decision log `0041`). A _mission_ is one case, reached by Chronotravel from the Navigation Table, rendered by `missionScreen()` as that case's own quest and nothing else; missions use the four teacher-swappable quest types (`mcq`, `sequencing`, `evidence-organizing`, `hipp`). An _Archive Challenge_ is a unit's extended written work (`saq`, `dbq`), reached from the Archive Terminal in the Archive Room and rendered by `archiveChallengesScreen()`. Don't put a swappable type in `unit.archiveChallenges[]` or an SAQ/DBQ in a case's slot — `tests/unit/retired-archive-challenges.test.js` fails on either.
- **A mission has exactly one name** (decision log `0042`, Phase 59): the name half of `case.title`, resolved through the teacher override by `resolvedCaseName()` in `main.js` — "The Exchange Ledger". **Every heading that names a mission uses `resolvedCaseName()`**, and the case number ("Case 1.02", via `caseNumberLabel()`) is an eyebrow above it, never inside it. Those used to be one sentence reading "uses `resolvedCaseName()` **or** `resolvedCaseTitle()`", and the two halves contradicted each other: `resolvedCaseTitle()` **is** the number joined to the name, so a heading built from it breaks the second half while satisfying the first. Seven did — the Navigation Table's route panel, the field screen, the mission card's kicker, the Practice Check's prose and three Manage Content headers — until Phase 107 (decision log `0106`). **The two functions differ only on Unit 1**, whose three titles are the only ones carrying a `"Case N.NN — "` prefix, so the wrong one of them reads correctly on twenty-four cases out of twenty-seven and puts the number in a 40px heading on the unit every student plays first. `resolvedCaseTitle()` survives for prose and labels — two Manage Content banners, the breadcrumb crumb, the atlas marker's `aria-label` — and for nothing else. Guarded twice: `main-case-numbering.test.js` asserts no case's name begins with a number, and `mission-naming.spec.js` asserts the rendered headings on three screens with `toHaveText`, because the defect is eleven characters at the front of a string and a containment check passes on exactly what it is meant to reject. `case.mechanic` is teacher-side help text only — don't render it as a name on a student screen. `case.shortTitle` means the _place_, used in Case 1.01's field-flow copy; it is not rename-aware, so never use it to name a mission.
- **A case says where and when it is set, once** (decision log `0107`, Phase 108). `caseWhereAndWhen()` merges `case.location` and `case.date` into one dateline, and three surfaces print it and nothing else about place or time: the mission screen's meta chip, the field screen's kicker, and the Preservation Case badge card. **`location` is authored in two shapes** — twenty-two of the twenty-seven cases carry their own date (`"Ellis Island, New York Harbor · 17 April 1907"`) and two are a bare place (`"The thirteen colonies"`) that needs `date` appended, which is Spine Review P10-3. The question the merge means is **"does the location already say when?"**; until Phase 108 it asked `location.includes(date)` instead — a proxy that holds only while the two dates are the same string, and for eight units the two readings were indistinguishable. Units 8 and 9 then authored a third shape, a location carrying the specific day a document was delivered against a `date` carrying the span the case covers, and got both: **"The United States Senate · 1 June 1950 · 1947–1954"**, live on Unit 8's mission chip and on its badge card whether earned or locked, with two more already written into Unit 9. The predicate is now whether the location names a four-digit year at all, because naming a year is the only thing `date` adds — where the location already names one, `date` contributes nothing to what is drawn, which was already true of twenty-two cases. **The e2e guard written for P10-3 had the same blind spot**: it asked whether a year _repeated_, and 1950, 1947 and 1954 are three different years, so it walked that screen and passed on every run. A guard that shares its subject's assumption is not a second opinion. `tests/unit/case-dateline.test.js` holds the rule over **all nine registered units** rather than the eight in `UNITS` — the only reason Unit 9's two were caught before the unit ships, and `0102`'s rule applied to content: key each guard to the table that answers its own question.
- **Field interior** — a room a field map opens into (Phase 65, decision log `0048`), declared on `FIELD_MAPS[unitId].interiors` and told apart by `progress.currentFieldRoom` (`null` means outdoors), resolved through `activeFieldMap()`/`activeFieldGrid()`/`activeFieldBlocks()`. Eight exist: Canal Crossroads' printing office and boardinghouse, Richmond's counting room and Chimborazo ward, Cottonwood Junction's land office and telegraph office, and Ellis Island's inspection hall and board of special inquiry room. **The inspection hall is the first interior bigger than the field viewport on both axes** (22×18), so it is the only room that takes `updateFieldPlayer()`'s follow-and-clamp branch rather than its centring one — still a pure function of player position, just not a constant one. **An interior declares exactly the fields an outdoor map declares** — that shape-equality is the design, and it is why collision, NPC behaviour, routing, proximity UI and record anchoring all work indoors without being told about rooms. Not a screen, not a portal graph, and never nested.
- **A prop's size is the pack's opinion, not the world's.** Every 1×1 object in these tilesets is drawn to fill its 48px tile whatever the object is, so the Institute's stool shipped painted 45px — exactly a character's standing body. Buildings (94–183px) and trees (129–142px) are the references genuinely in proportion to the 45px cast; small props are not, so measuring a new one against its neighbours will mislead you. Replacements are generated to size (the canvas _is_ the scale) and packed through `derived-objects.manifest.js`. **Adding a sheet to a palette means adding its `import.meta.glob` in `main.js` too** — `createTilesetImageResolver()` throws on a missing one and the whole map renders as an empty frame; that has now happened twice.

If you move an object in a `scripts/generate-*-tmj.js`, move its `marker` rect too. Restyle `.hub-marker` in place in `global.css`; appending an override layer is how the three competing styles this replaced came to exist. NPCs keep their own treatment (name below the sprite).

## Gameplay invariants (regression-prone areas)

These patterns recurred as bugs across many hotfix milestones (3.4.5 through 3.4.15 in the decision log) — be deliberate when touching this code, and visually re-test rather than trusting a syntax check.

- **Camera must stay a pure function of player position.** `updateFieldPlayer()` / the hub equivalent recompute `fieldCamera`/hub transform every tick from `fieldMovement.x/y` (clamped to viewport bounds, integer-rounded to avoid blurry text). Don't introduce `scrollIntoView()`, `.focus()`-triggered scrolling, or click-handlers that move the camera toward a clicked DOM element — several past regressions came from exactly that.
- **Proximity-gated interaction.** NPCs/objects only become interactable within a reach radius (see `targetDistance`/`targetReach`/`nearestHubTarget` for the hub, and the analogous field logic) — both `E` keypress and click should require the player already be in range, not act as a teleport-and-interact.
- **One interaction prompt at a time**, cleared when dialogue closes, the player moves out of range, the screen changes, or progress resets — watch for stale "Press E" prompts or duplicate prompts after refactors. **The field's equivalent is `#fieldNotice`, and it is a status line rather than a prompt** — the field has no "Press E" surface at all (`.field-interact-prompt` was swept as dead CSS in Phase 45D; a marker's own label appearing on approach is what names it). It is written only by `fieldTooFarNotice()` and `refuseLockedRecord()`, and until Phase 90E nothing ever took it back: it cleared on arrivals and not on the player doing what it asked, so "Move closer to interact with Taíno canoe worker." survived the walk to a different NPC, that whole conversation, and every record read after it. **An attempt that lands clears the line left by one that missed** — that is `toggleFieldDialogue()` / `openFieldRecord()` / `beginFieldRecord()`, and a fourth writer of this line has to clear it too.
- **Dialogue renders anchored to the speaking NPC**, in a layer that doesn't force the world transform to reset or the document to scroll. The bubble is a flex column whose content lives in `.field-speech-bubble__scroll` — anything added to it goes inside that child or it will not scroll — and `placeFieldDialogueBubble()` puts it on whichever side of the speaker has more room, caps it to that room, and lets the rest scroll. **Check the cascade before the arithmetic here.** Two rules in this area were dead for a full phase and neither failed loudly: `--below`'s flip lost to a `transform: … !important` restated further down `global.css`, and `:has(.field-interview) { width: 404px }` lost to the base rule's `max-width`. Both were found by measuring in the browser, not by reading the file (decision log `0052`).
- **A suite too slow to reach a bug cannot report it.** Phase 93 measured Playwright at two workers
  instead of six: the page runs at 40+fps instead of 4-13, and the same seven spec files that pass
  21/21 at six then failed four or five, three runs in three. Neither cause was a defect in the
  game. **Five specs read the world transform the frame before it is written** — the field mounts
  `translate(0px, 0px)` and the first `updateFieldPlayer()` writes the real camera a frame later,
  so a one-shot read between the two returns 0 and fails as "camera x 0 vs -964", indistinguishable
  from the camera-purity regression those tests exist to catch. They are `expect.poll` now, which
  is what reading a value written asynchronously after mount requires; waiting for "non-zero" is
  not available, because one room's legitimate centred value is 10. **And the suite's longest walks
  were calibrated to a slow page**: `walkTo` slid past obstacles rather than pathing round them, and
  at full speed the player reaches those obstacles and runs out of stall budget. Four repairs to the
  slide were measured and all failed — teaching it to reverse fixed the one walk it was built for and
  **broke five others**, because a walker that steps one way and then the other resets `stalls` every
  burst and burns the clock instead of stalling out. **There is no tuning of a blind walker that is
  not that trade**, so Phase 94 stopped tuning it and gave it the walls: `window.__chronicleNav`
  samples the game's own `isFieldBlocked`/`isHubBlocked` and `walkTo` breadth-firsts the result. Both
  `nudgeTo` workarounds went with it, and `workers: 2` shipped. **Before tuning a walk that started
  failing, check whether the machine got faster rather than the map changing.** See `0092` §5 and
  `0093`.
- **A test helper may read the game's state; it must not restate the game's rules.** The walker's
  route comes from `isFieldBlocked`/`isHubBlocked` through a dev-only probe, not from a second reading
  of the `.blocks.js` modules — so a wall that moves moves for the walker too, and there is no second
  collision rule to keep in step. The lattice is **half a tile**, because the foot box is 0.68 wide
  and a full-tile lattice cannot reliably see a one-tile gate. The probe is gated on
  `import.meta.env.DEV`, exactly as `?warp=` is, and is verified absent from `dist/`. Two properties
  the first version lacked, both found by running it rather than reading it: **a route is a snapshot,
  not a promise** — it includes the other bodies, because both predicates do, so a leg that stops
  making progress re-plans rather than shoves — and **a route is not a tracker**. The old walker
  re-read its target every burst and followed a patrol for free; a route is planned once, and
  `settlement-carpenter` walks the length of the settlement, so the first version arrived perfectly
  at where he had been standing. The route carries the goal it was drawn against and re-plans when
  the target leaves it. See `0093` §2.
- **A per-frame path patches the DOM; it does not render.** `updateFieldNpcs()` and `updateFieldProximityUi()` say so, and Phase 90E paid to learn it applies to state changes too. Walking away from a conversation clears `activeFieldNpc`, and the bubble that state drew has to go with it — but making the movement loop `render()` (what every deliberate exit does) repaints the map canvases on the frame a player starts walking, and turned **four unrelated e2e specs red under parallel workers while they stayed green at `--workers=1`**. `closeFieldDialogueOnMove()` removes the one node instead. The general lesson was recorded as **an e2e suite can only report a performance regression as a correctness failure**, so several specs failing at once in an area nobody touched is one cause, not several flakes — still true of the _diagnosis_, and Phase 93 found it false as a _design_. A walk that parks short fires just as readily for a busy laptop, and the suite spent every run since reporting 2-8 red tests for that reason while claiming to watch for this one. `tests/e2e/frame-budget.spec.js` measures the claim itself instead: `render()` assigns `app.innerHTML` wholesale and so removes every direct child of `#app`, while the per-frame path patches attributes and single nested nodes and never does — so a `childList` MutationObserver on `#app`, without `subtree`, counts renders and **does not care how fast the machine is** (verified at 4-9fps: 0 for a walk, 1 for a deliberate exit). Re-adding `render()` to either movement loop reds it 100% of the time at any worker count. **The third assertion is what keeps the other two honest** — a deliberate exit must still count 1, or a broken observer reads as a passing test. See `0092`.
- **A body you are already standing inside does not block you** (Phase 112, decision log `0111`). `isHubBlocked()` has called the exported, unit-tested `isBlockedByBody(next, here, bodies)` since Phase 64 for this reason — without the `!rectsOverlap(here, body)` clause an overlap has no exit, because every candidate step still overlaps and every direction is refused including the way out — and **`isFieldBlocked()` never took it**. Two ways to reach the state. The narrow one is permanent and about three pixels wide: an NPC checks itself against the player with `fieldNpcFootBoxAt` (±0.36) and the player is blocked by `npcFootBox` (±0.42), so between 0.70 and 0.76 tiles apart the NPC has legally stepped somewhere the player's own collision calls occupied. **The three foot boxes stay three** — narrowing one to match would change how close a player may stand to everybody in the game, which is a feel change and not a bug fix. The wide one is a lock the game reaches unaided: `exitFieldInterior()` restores `progress.fieldReturn` verbatim and never asks whether anybody has since walked there, so an interior exit or a restored save can put the player inside a stationed body with no way out but a reload. Banked in `field-movement-dialogue.spec.js`, which measures the overlap off both elements and reads the player's own cell back through `window.__chronicleNav`. **`isFieldBlocked()` is not exported and should not be** — it reads `activeFieldMap()` and `fieldMovement`, so a unit test of it would test module state; the primitive under it has been unit-tested since Phase 64.
- **NPC movement respects the same collision as the player** (`FIELD_BLOCKS`/`HUB_BLOCK_RECTS`, land checks via `isCaribbeanLand`) and swaps sprite sheets by facing direction rather than sliding a front-facing sprite sideways. Since Phase 60 that means four real directions — `down`/`up`/`left`/`right`, each its own horizontal walk strip on the shared 48×56 canvas (`engine/sprite-animation.js`, `CHARACTER_SHEETS` in `main.js`). There is no mirroring and no `side` sheet: `up` used to be the south sprite tinted darker and `left` used to be east flipped, and both are real art now. Column 0 of every strip is a standing pose for that direction, which is how a character keeps facing the way it last walked. **The 48×56 canvas is pinned, not derived** (Phase 64): `canonicalCanvas()` in `scripts/assets/build-character-sheets.js` clamps to `SPRITE_CANVAS` rather than sizing itself from the widest cast member, so adding a character with a long prop clips that prop instead of silently resizing all 140 committed PNGs and invalidating the CSS tokens and visual baselines with them. Change `SPRITE_CANVAS` deliberately if the canvas must ever move; don't let a new character decide it.
- **An NPC has a job** (Phase 62, decision log `0045`). `FIELD_NPC_BEHAVIOURS`/`UNIT2_*`/`UNIT3_*`/`HUB_NPC_BEHAVIOURS` map an id to one of three kinds, defined in `engine/npc-behaviour.js`: `station` (stands at `at`, turns to look around), `route` (walks a circuit of `stops`), `wander` (a disc around `home`, Phase 61's behaviour). All seeded per NPC id, so a character behaves the same way across reloads.
  - **A route is authored as places, not waypoints.** `engine/npc-routing.js` pathfinds between consecutive stops over the map's walkable cells, costing a road cell a quarter of open ground so people use the road; road cells come from the generators as `*_ROADS` in `<map>.blocks.js`. Don't hand-write intermediate waypoints — name the two or three places the person has business being.
  - **Authoring cannot strand anyone.** A stop snaps to the nearest open cell, an unpathable leg is dropped, a route left with nothing degrades to a station, and every step is still gated by `isFieldNpcBlocked`/`isHubNpcBlocked`. `tests/unit/field-map-coordinates.test.js` fails if a shipped route never reaches a stop.
  - **Two people must not share ground.** `nearestFieldInteraction()` answers with whoever is closest, so a player who walked to one gets the other. This shipped twice — the Powhatan pair by overlapping wander discs, the burgess by a _route whose path_ ran 1.1 tiles from the stationed minister while its stops were a comfortable 2.9 away. The coordinate test measures a route's whole walked path, not its stops, against a 1.5-tile bar (just above the 1.45 interaction reach).
  - **A person and a piece of furniture must not share ground either** (Phase 90C, decision log `0080`). The doorstep-NPC hazard above is one instance of a general rule, and the Institute had the other: Prof. Park's route stopped 1.4 tiles from the Navigation Table, inside its 1.65 reach, so `E` at the table opened the professor. Two things were wrong and both had to be fixed — `nearestHubTarget()` was `Array#find`, so despite its name it answered in **`HUB_TARGETS` declaration order** rather than by distance (it is `nearestInReach()` now, exported and unit-tested), and a body parked in the room's one approach is still wrong with the sort fixed. Post staff two and a half tiles clear of an interactable object; `field-map-coordinates.test.js` now asserts it for the Main Hall. **The seven field maps are swept too as of Phase 90E**, at a different bar and deliberately: each target's own reach (1.55 for an object-anchored record, 1.45 for a door), not 2.5 — because 2.5 is right for a room whose one approach is a doorway and wrong for a market square, where a notice board is meant to have people walk past it. It measures `territoryOf()`'s **walked path**, which is the only thing that catches this: Philadelphia's town crier came 1.39 tiles from the Assembly hall notice board while his stops sat a comfortable 1.98 away, so mid-stride the broadside opened the crier. **Only `E` ever went through that sort** — `handleHubClick`'s `hub-interact` passes `dataset.target` straight through — which is why a mouse never reproduced it and it survived for many phases behind a workaround button in Julian's own dialogue.
- **`E` and a click must reach the same thing the same way, and when they don't it is the keyboard that is wrong.** This has now shipped twice and **both times the pointer path was the correct one**, so neither bug is reachable by anyone testing with a mouse. Phase 90C: `nearestHubTarget()` sorted by declaration order while `hub-interact` passed its id straight through. Phase 90D (decision log `0082`): `nearestFieldInteraction()` offered a record whose marker `fieldSourceSignal()` deliberately does not draw — a locked one — so the gate the click path could never reach was the only gate in the game, and **Richmond's price board opened**. The rule that falls out: **when a control exists in two forms, the state changes live in one function both call.** `nearestInReach()`, and `openFieldRecord()`/`beginFieldRecord()`, are that shape. A third path into a record must go through those two, and a record's availability is `sourceAvailability()`'s answer, asked by `refuseLockedRecord()` and nowhere else — **do not add a case-id literal beside it**, which is the half of Phase 70's fix that got left behind for five more units. `tests/unit/field-record-gate.test.js` fails if either literal returns or a third entry point appears. **`toggleFieldDialogue()` is the third of these** (Phase 90E, decision log `0083`) — `E` and a click carried character-for-character copies of the dialogue toggle, caught before they drifted rather than after. **That rule has a dual, and both are worth carrying because different habits catch them** (Phase 90H, decision log `0086`): **when one variable answers two questions, the second question gets the first one's answer.** `sourceOrigin` said both where the reader goes back to and where the Codex goes back to, so opening a record from the Codex destroyed the Codex's memory of the Institute and its "← Return" fell through to the field — five ordinary presses from the Archive Room's own side panel. The duplication rule is found by diffing two call sites; this one cannot be, since there is one assignment and one read and each is locally correct. It is found by asking what a name means, and `origin` does not say origin _of what_. `codexOrigin` is the second variable; a third reader of either belongs to whichever question it is asking.
- **A door is an interaction, and it competes for the same reach.** A field interior's door is a third kind in `nearestFieldInteraction()` alongside `npc` and `source`, at the same 1.45-tile radius and in the same nearest-wins sort — walking over a threshold does nothing. The cost lands in authoring: **post a doorstep NPC two and a half tiles clear of the door**, or the person wins the sort and the room becomes unreachable from every approach. That has now shipped twice — Canal Crossroads' editor a tenth of a tile from his own shop's threshold, and Unit 6's register and telegraph operator four tenths and half a tile from theirs, which would have left both Cottonwood Junction rooms unenterable. **Nothing in the suite catches this**: the conflict is between a door and an NPC, and `field-map-coordinates.test.js` measures NPC against NPC. Check a new interior's door cell against the outdoor cast by hand.
  - **An interior must be attached after the `FIELD_MAPS` literal, not inside it.** A room's `blocks` const is declared further down `main.js`, and reading one from inside the literal is a temporal-dead-zone `ReferenceError` that takes the app down on boot.
  - **Every field surface must declare `isLand`**, or `map.isLand is not a function` throws on the first movement frame. Interiors use the shared `interiorGround(grid)` factory — a plain in-bounds test, because a room's walls are collision rects, not a coastline.
  - **A room smaller than its frame centres; it does not clamp.** The outdoor follow-and-clamp formula degenerates to a top-left pin once the world stops being bigger than the viewport. This is still a pure function of player position — for a small room it is a constant one, so the camera invariant holds.
  - **A record draws only on its own surface; the checklist lists them all.** A case's `sources` is the whole case's list everywhere, so `fieldSourceSignal()` guards per-surface — without it, records from elsewhere stack on `sourcePointPosition()`'s (10,10) fallback in the middle of the room. The **Mission Tracker** is deliberately the opposite and resolves anchors across _every_ surface of the unit's map, because it is the only thing that says there is anything behind a door at all.
- **Nothing in the game looks at where a character's name pill lands, and bodies clearing does not make labels clear** (Phase 113, decision log `0112`). The recorded hazard is a pill against a `base`-solidity overlay row; there are two more axes and neither is measured. **Pill against pill**: the coordinate suite's NPC-versus-NPC bar is 1.5 tiles and a pill is about **2.1 tiles wide**, so the lending office's two staff overlapped while posted exactly two tiles apart, on purpose, with a comment approving it. **Pill against the frame**: `.field-npc span` carried `white-space: nowrap`, so Ellis Island's 300px "Surgeon, Public Health and Marine-Hospital Service" lost its last word off the edge. Pills wrap now, capped at four tiles — and **`width: max-content` is load-bearing there, not tidiness**, because the pill is absolutely positioned inside a 48px NPC button and dropping `nowrap` alone makes it shrink-to-fit against that instead, wrapping every label in the game. The cap **bounds the overhang and cannot remove it**: a pill centred on a body at the frame edge overhangs by half its width whatever that width is, which is ordinary camera behaviour and accepted. **None of this is visible to the visual baselines**, which hide `[data-npc]` before every screenshot. **One axis of this is now measured and the rest are not.** `tests/e2e/cast-legibility.spec.js` samples the `.field-world-overlay` canvas under each pill's own text box and under each 48x56 sprite box, across all eighteen field surfaces (Phase 114, decision log `0113`) — because that canvas holds precisely the art that draws _above_ the cast, so the question can be asked in the units it is about rather than through tile arithmetic. It caught something the eye provably cannot: Riverbend's third watchman stood inside a maple with **76% of his body and 98% of his name** painted over, and a by-eye sweep of that map listed two watchmen where the table has three, because there was nothing on the map to look at. **The `.tmj` would have given the wrong answer** — `tilesForFrame()` anchors an oversized tile by its bottom edge, so a canopy reaches several rows up from the cell that carries it. Caps are 8% of the text box and 55% of the sprite box, set between the measured defects (24.2 and 97.6; 76.1) and the highest accepted readings (2.2, a lamppost finial; 31.5, a preacher standing beside a maple). **Whole-pill coverage does not separate them** — 20.9% behind a rounded corner reads clean and 21.7% through two lines does not — so the box is inset to the glyphs by the pill's own CSS padding. **Stations only**, because a route or wander NPC crosses overlay rows by definition and a sample of one reports the frame rather than the post; a mover is held instead to the ground its job covers, which is how the disc check in the next entry works. Everything else here — pill against pill, pill against the frame, a body on furniture — is still not answerable from a canvas and there should still not be a clever test; look at the room.
- **A name pill is wider than a body and hangs below it, and the player is not in the NPC table.** Common Cause gave Emery Voss a comment reading "3 tiles clear of the free tradesman's disc" and gave the spawn 0.74 tiles: every _person_ on the map was cleared of that wanderer and the square the game stands the player on was not, so his label opened the map drawn across the Chronicler's head (Phase 114, `0113`). `cast-legibility.spec.js` now checks a wanderer's **whole disc** against the spawn rather than a sampled frame. **A rule kept in a table only protects what the table contains** — the same shape as `0102`'s map that no guard could see because every guard keyed off the playable table.
- **Field interiors are checked for rects in bounds and rects backed by art** as of Phase 113, which the outdoor maps and both hub rooms have had for phases and the ten rooms had not — their block asked only whether a room could be walked, never whether its walls are where its walls are drawn. Both came back clean on all ten. The art check asks whether **any** tile layer has paint in the cell, because an interior's solid things are spread over more layers than an outdoor map's single `structures`, and it carries a non-vacuity assertion because a filter over an empty list passes. `--cast-label-top` hangs it a fixed distance below the feet, so any `base`-solidity object whose overlay row a character can stand on will draw over the label — Unit 6's land office cut the register's name in half with its own counter rail. Five of the eight interiors now have such objects, and Unit 7's inspection hall has two — its rails are stamped `base`, so anyone posted within about 1.6 tiles of the row above one loses their name to it. There is no test for it and there should not be a clever one; look at the room.
- **A per-unit table with a sane fallback and no test is how a whole unit ships broken**, and this has now happened twice. **A new field map costs a `FIELD_COPY` entry, and forgetting one is silent.** `fieldScreen()` falls back to Unit 1's briefing when a map has no entry of its own, so a map that skips it tells its player to "follow the shoreline toward the Spanish camp." Unit 6 shipped with exactly that and it took a browser to see it; `tests/unit/field-map-coordinates.test.js` now asserts one entry per `FIELD_MAPS` key, reading `main.js` as source because the table is not exported. **`UNIT_MAP_VIEW` is the same table in another file and it cost three missions** (Phase 90I, decision log `0087`): it stopped at `unit-05`, so Units 6 and 7 fell back to the Atlantic view and four of their six Navigation Table markers projected outside an `overflow: hidden` atlas — and since `unlockNext()` unlocks a case without selecting it and `select-unit` only selects a unit's first, **a marker off the map is a case that cannot be started at all**. `tests/unit/navigation-table-views.test.js` is that table's equivalent guard. When you add a third per-unit table, add its test in the same commit.
- **A sequencing quest must be authored out of order.** `renderSequencingQuest()` lays items out in the authored array's order and never shuffles, so `items` written `position: 0,1,2,3,4,5` render already solved and grade the student correct for touching nothing. Keep each item's `position` right and its place in the array wrong. This is a **failing test** as of Phase 81F rather than a convention — `tests/unit/sequencing-quest-order.test.js` sweeps every unit's sequencing arrays through `loadChronicleContent()`, so a sixth unit is covered the moment its arrays are registered. It went five-for-five as prose alone.
- **A scripted beat moves characters, never the screen** (Phase 63, decision log `0046`). Every scene works by writing to the same objects the ordinary loops already read — an NPC's own behaviour state and `instituteMovement` itself. That is what keeps the camera a pure function of player position with no new code path, and it is why `engine/cutscene.js` has **no camera command and never will**; if you add a scripted moment, move the bodies. `engine/escort-walk.js` is a pure primitive (leader walks a `findRoute()` path, follower samples that trail a fixed distance behind, needing no collision test of its own because the leader has already walked every point of it). **There is now one scripted-scene code path, not two** — Phase 81G folded the Entrance Hall's bespoke `hallwayScene` onto the `engine/cutscene.js` interpreter, so a scene is a list of commands in `content/cutscenes.js` and `main.js` hosts it. **A scene that needs something the eight commands cannot say wants an `onDone`, not a ninth command**: `startHubScene(id, { onDone })` is how the Entrance Hall changes rooms when it ends, because where the screen goes next is host state and a content file has no business naming it.
- **One input lock, `isHubInputLocked()`.** Every scripted beat suspends player control through that one predicate, checked at the same three sites — the institute keydown branch, `runHubMovementLoop()`, and `interactWithHubTarget()`. Adding a second lock concept checked at an overlapping subset of those is how a screen ends up controllable during half of a cutscene. Anything that locks movement must also suppress the "Press E" prompt, or it hangs there offering an interaction that is already happening. It was three terms, then two, and is **one** as of Phase 90 — `isHubSceneActive()` — because the Main Hall's tutorial tour stopped being a caption panel with its own lock and became `director-tour`, a scene like any other. Keep the function anyway; a bare predicate at three call sites is what stops a second one appearing beside it.
- **Ground speed drives the walk cycle, per body, per moment**, and **the field's one non-constant case is the wall slide** (Phase 112, decision log `0111`): `fieldHeldVector()` normalises a diagonal by root-half, so a diagonal held against a wall keeps only one of its two components and the body travels at 0.707 x 3.65 = 2.58 tiles/s — while `updateFieldPlayer()` handed the sprite the constant 3.65. `updateFieldPlayer()` takes a speed now, as its hub twin has since Phase 63, and the loop **measures** it (distance actually travelled over the frame's own elapsed time) rather than special-casing the slide, so any future path that moves the player some other way is covered by construction. Guarded in `field-movement-dialogue.spec.js` by reading `--sprite-cycle` off the sprite: 0.301s walking free, 0.426s sliding. **Facing is written from raw input, before collision, and that is deliberate** — walking into a wall turns the body without moving it, which is how a player aims every proximity interaction in the game. `updateInstitutePlayer(speed)` takes the player's _current_ speed rather than assuming `HUB_SPEED` (3.65): a scripted walk travels at `SCENE_WALK_SPEED` (2.2), and passing the default there would run their legs 66% faster than their feet. Same rule as `walkCycleSeconds()` everywhere else — if something moves a character at a speed that isn't the usual one, it has to say so. **A second loop writing the same sprite is the same bug wearing a hat**: the 30Hz `updateInstituteNpcs()` interval used to run straight through scenes, repainting the player at the default speed ~30×/s while the scene's own frame painted it at the scripted one, so the walk cycle stuttered between 0.301s and 0.5s. It stands down while `isHubSceneActive()`.
- **A follower ends a walk a gap behind the leader, never on top of them** (`engine/escort-walk.js`, Phase 90). Two related things are easy to get wrong here and both shipped: the trail is seeded from the **follower's** own position at negative arc length, or the follower teleports onto the leader's path the first frame it engages; and `snapActor()` in the scene runner has to move the follower too, reading `command.follower` rather than `hubScene.followsPlayer` — skip never runs `moveActor`, so that field is stale by definition. Both were invisible until a second scene used a follower.
  - **A stationed NPC is furniture to everyone else.** Their posts go into `createNavGrid`'s `occupied` list, or a route planned through one leaves that person blocked against them for good.
- **Four numbers tie the cast to the world, and none of them should be eyeballed.** `--cast-h: 56px` renders the 48×56 canvas 1:1 against 48px tilesets — don't reintroduce a per-viewport override, since fractional scaling is what it exists to remove. `--cast-foot` is a world offset scaled by `--tile`, and its value per surface is that surface's collision foot-box centre (`FOOT_ANCHOR` in `engine/sprite-animation.js`); when it drifted from that, the Institute drew everyone a full tile below where collision held them. `--cast-label-top` hangs a character's name pill a fixed distance below `--cast-foot`, so one expression puts it under the feet on both surfaces; written against the button's own box instead, it tracked the hit area, and the field's pill sat across everyone's boots through six re-tunings. Walk-cycle duration comes from ground speed through `walkCycleSeconds()`, never a fixed value — a hard-coded cycle is what made the player glide and the NPCs skate.
- **The Director's dialogue box is a fixed three lines, and `.director-dialogue-box__text` is shared** (Phase 91, decision log `0090`). The box used to grow from one line to nearly four as the typewriter ran, moving the caret, the buttons and the reveal card above it on almost every character; it is now `height: calc(var(--dlg-lines) * var(--dlg-line))` with `overflow: hidden`. Two things follow. **The class is not the director's alone** — `hubSceneDialogueMarkup()` renders it inside `.hallway-dialogue`, so the Entrance Hall, the Main Hall tour and every Voss scene speak through the same rule; the fixed-height treatment is scoped to `.director-scene` and the base rule must stay as it is, with the three institute-room baselines as the check. And **`overflow: hidden` truncates in silence**, so the size is chosen against the content, not against a mockup: the longest authored body is 215 characters and the guard is in `intro-sequence.spec.js`, asserting `scrollHeight <= clientHeight + 1` on every fully-typed line. If a new line overflows, that spec is the thing that says so — do not raise `--dlg-lines` without re-measuring the breakpoint you are raising it for, and keep `--dlg-line` equal to `--dlg-size` × 1.5 by hand when overriding either.
  - **One custom property, one owner per breakpoint.** The narrow-viewport overrides use a _closed_ range (`min-width: 701px`) rather than two open `max-width` queries. With both matching, Chromium used the wider rule's `--dlg-lines` inside the height `calc()` while `getComputedStyle` reported the narrower rule's — the CSS read correctly and the browser did otherwise.
- **The Director on the intro screens is a plate, not a walk sheet** (Phase 91). `DIRECTOR_CUTOUT` is a 484×1359 cutout in `assets/plates/`, referenced by a **static string literal** inside `new URL()` like every plate, and deliberately absent from `CHRONOTRAVEL_PLATES` — that table is keyed by destination and its test asserts every key is a shipped unit. It is **not** in `assets/institute/`: that folder is the 48×56 walk-sheet tier with a 50 KB budget and a 7-column canvas `character-sheet-geometry.test.js` asserts. `CHARACTER_SHEETS.director` is untouched and still what the hub rooms draw. **No `image-rendering: pixelated` on it** — the art is still pixel art, but the scene downscales it 0.43×, and nearest-neighbour at a non-integer ratio shreds an anti-aliased outline.
- **The Codex reveal is a screen, and it owns the input while it is up** (Phase 91). It is injected on demand and removed on dismiss — never rendered as an empty shell, because an `inset: 0` element with a background reports as _visible_ to Playwright even when empty, which is the same lesson `.director-extra-content:not(:empty)` carries. Three input paths have to agree: the click resolves through `closest("[data-action]")` so "click anywhere" is free; `.director-scene__bar` takes `inert` so the buttons underneath cannot be tabbed or Entered through the veil; and `handleWindowKeydown`'s intro branch checks for the veil **before** its Enter/Space advance, or the briefing walks forward behind it. It also fires _after_ its line rather than before — from `finishLine()` and from `advanceIntroDialogue()`'s skip path, which never passes through `finishLine()` — and a replayed step restores the small rail card without re-veiling.
- **A finished quest renders as a record, and the record is sealed at both ends** (Phase 92, decision log `0091`). `renderQuest(questType, quest, state, { readOnly: true })` is the fourth argument every one of the six types takes; it is what the completed-mission card uses, and it exists because `archiveChallengeQuestCard()` grades on **every render** — there is no submit step anywhere in this codebase — so re-rendering a finished quest _editable_ lets a nudged record flip "Mission complete" back to a hint while `completedCases` still has the case archived. Both ends, or neither: **every renderer disables its own controls _and_ `isSealedQuestTarget()` refuses in `handleAppChange`, `handleAppDragstart`, `handleAppDrop` and the `sequence-move` action.** Markup alone is not a lock — a drop target has no disabled state at all, a disabled input is one devtools attribute away from live, and a synthetic `change` dispatches on a disabled control quite happily. The guard reads `data-quest-readonly` off the quest root, so it is **derived from the render rather than kept in step with it**; the drop guard is not a mirror of the dragstart guard, because the drop target is a different element from the drag source. Same shape as the activity engines' filed-record rule above.
  - **Textareas go `readonly`, not `disabled`** — a disabled textarea greys its own text out, and showing that writing back is the whole reason the mode exists. Radios, selects and buttons go `disabled`.
  - **The mode is applied to the completed mission only, deliberately.** A completed Archive Challenge stays editable because SAQ/DBQ "complete" means submitted and the card underneath offers "Get feedback on my revision →"; the Practice Check stays editable because its own copy says re-answering never affects progress. The capability is one argument away for either.
  - **A record says things the form does not.** The evidence quest's select drops its dropdown arrow and its label turns from "Place in" to "Filed under"; the sequencing record hides its ↑/↓ pair and numbers the rows with a CSS counter, because `.quest-sequence-list` is `list-style: none` and the buttons were the only thing making the order legible as an order; and `.evidence-card--placed`'s 55% fade is overridden, since in a finished record every card is placed and the fade would veil the whole answer.
  - **The regression that would ship silently is the _default_ render.** A renderer emitting `disabled` unconditionally locks the live form on every screen in the game, and every other test in the suite would still pass — they all render the default and none asserts the absence of an attribute nobody had thought of yet. `tests/unit/quest-read-only-mode.test.js` asserts it for all six.
