# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The current game is **Chronicle**, an AP U.S. History RPG: a browser-based, top-down field/dialogue game. It covers **CED Periods 1–7 of 9** as of Phase 89C — twenty-one cases across seven units, all with real, cited historical content, on seven walkable outdoor field maps plus eight interiors. Unit 1 "The Atlantic World" (case-001–003), Unit 2 "Colonial Crossroads" (case-004–006), Unit 3 "Revolution and Founding" (case-007–009), Unit 4 "Democracy, Markets, and Reform" (case-010–012), Unit 5 "A House Divided" (case-013–015), Unit 6 "A Continent on Paper" (case-016–018), Unit 7 "The Terms of Belonging" (case-019–021). **Units 1–6 reached parity in Phase 87** — Unit 6's map shipped in Phase 85, its two interiors in Phase 86 and its three activities in Phase 87. **Unit 6 is complete as of Phase 88**, when its Meridian reveal shipped — the last thing it was owed. **Unit 7 became playable in Phase 89C**, when its wharf at Ellis Island shipped and the `UNITS` line was added — so the game a student can walk is now Periods 1–7 — its two interiors shipped in Phase 89D, and **its three missions shipped in Phase 89E, which completes it**. **All seven shipped units are now at parity**: every one has a walkable map, its interiors, and three playable missions on it. Four of Unit 7's seven records keep `activityRoute: null` and open in the reader, which is what every non-mission record on the other six maps does — three missions is the slate, and seven activities would be a different design. See `docs/decision-log/0081-three-missions-at-the-immigrant-station.md`.

**"Republic Builder Engine" is retired as the project's identity, and as of Phase 81 the string is gone from every rendered surface.** The repository was originally framed as a reusable engine of that name; that framing is no longer current. The eventual multi-subject platform this codebase may grow into **does not yet have a final name** — don't invent one or reintroduce "Republic Builder" branding in new code, docs, or copy. `BRAND.engine` no longer exists (removed from the content file, `BrandSchema`, and its ten render sites), the chrome header is now a one-line lockup, and the tab title, `package.json` name and README front matter all say Chronicle. Two survivals are deliberate: the `localStorage` key `republic-builder.chronicle.unit-01.v2`, because renaming it orphans every existing save, and the repository folder name itself. **Don't "finish the job" on either.**

**Removed systems — do not restore:** Founder Paths, professions, Historian Skills, and clothing/wardrobe-slot systems have been removed from the design and must not be reintroduced. The player identity model is intentionally minimal (display name + one of two appearance choices only — see `docs/decision-log/0005-chronicle-identity-and-first-field-entry.md`); pronouns, wardrobes, professions, cosmetics, and inventory remain deliberately out of scope, not merely deferred to a later milestone.

### Product intent

The goal is a Pokémon-inspired APUSH RPG students use across a full school year — approachable controls, a stylized explorable world, NPC dialogue bubbles, independent NPC movement, location-specific music, and badge/collection progression — not a quiz site or worksheet reskin. Gameplay is meant to train authentic AP U.S. History skills (HIPP source analysis, SAQ/LEQ/DBQ argument construction, evidence-based reasoning) using real primary sources and the actual College Board rubrics where applicable, rather than relying on trivia recall. Game progression must never grant unfair advantages on graded assessments — cosmetic rewards, organizers, and alternate routes are fine; pay-to-win or build-to-win mechanics on assessments are not.

Narrative frame: the player is recruited at the Chronicle Institute (present day) because the historical record has become damaged/unstable, becomes a "Chronicler," and uses "Chronotravel" to visit historical settings, gather evidence from people and primary sources, and transmit/preserve records back at the Institute Archive to earn area badges. Historical dialogue may take reasonable dramatic liberties but should stay in the speaking character's voice — avoid fourth-wall commentary, repeated "this is dramatized" disclaimers inside conversations, or modern educational narration coming out of a historical figure's mouth.

## Commands

Run from the repo root (npm scripts shell out to Vite, which is rooted at `apps/web` via `vite.config.js`):

- `npm run dev` — start the Vite dev server (opens the browser automatically)
- `npm run build` — production build (output in `apps/web/dist/`)
- `npm run preview` — preview a production build
- `npm run validate:content` — real, working Zod-based validator (144 schema/cross-reference groups as of Phase 89). Validates all seven registered units' `unit-0N-campaign.js` and `quests/unit-0N-quests.js` against schemas in `apps/web/src/content/schemas/`, plus the 9-unit primary source library, and checks global case/source id-uniqueness, per-quest-type id-uniqueness, case-period-matches-unit, and every archive/investigation/reader/alternate challenge cross-reference. **Its per-unit blocks are hand-written** — adding a unit means adding lines by hand in `scripts/validate-content.js` (schema block, `questArraysByType`, the cross-reference lists) and in `apps/web/src/repositories/local-content-repository.js`. See `docs/content/CONTENT-VALIDATION.md`.
- `npm run lint` — real, working ESLint flat config (`eslint.config.js`)
- `npm run format` / `npm run format:check` — real, working Prettier

A test runner **is** configured: `npm run test` (Vitest, non-watch, CI-compatible) runs tests from `tests/unit/` — see `docs/development/UNIT-TESTING.md`. ESLint and Prettier **are** configured and working — don't claim otherwise.

Type checking is **editor-only and advisory**, not a gate. `jsconfig.json` turns on `checkJs` for `apps/web/src/engine/**` and `apps/web/src/repositories/**` only — everything else, `main.js` included, is unchecked. There is no `npm run typecheck` script and TypeScript is not a dependency; measure it on demand with `npx -y -p typescript tsc -p jsconfig.json --noEmit`. The current baseline is **16 errors, all verified false positives** (untyped `supabase-js` embeds inferring `{}`/arrays, `number[]` where a `[x, y]` tuple is wanted, and Safari's `webkitAudioContext`) — so treat a _new_ error as worth reading, but don't "fix" the standing 16 by changing engine code.

Spell checking is configured in `cspell.json`, with word lists in `.cspell/` — `project-words.txt` (domain/engine/tooling vocabulary) and `source-quotations.txt` (period spellings quoted verbatim from primary sources, which must **not** be "corrected"). The repo is calibrated to zero unknown words, so any hit is a real typo. Check with `npx -y cspell "<glob>"`. Note that `19th Centruy European Dock`, `Labratory`, and `Jamestown Capenter` are misspelled _upstream_ — on disk and in PixelLab respectively — so those strings are correct in code and must stay.

## Architecture

### The app is currently one file

The entire running game is implemented in **`apps/web/src/main.js`** (15,984 lines as of Phase 90H / 2026-08-23 — re-check the line count with a quick `wc -l` before citing it if much time has passed, don't trust a stale figure, and use `wc -l` rather than PowerShell's `Measure-Object -Line`, which under-reports this file by ~340 — this file has grown substantially phase over phase and old figures go stale fast). It owns: screen routing/state machine, field and hub movement/collision/NPC patrol logic, dialogue, the activity host screen, the exchange ledger, the Author Mode panel, quest rendering/grading, the join/login/teacher-dashboard/grading/manage-content screens, and all HTML rendering (via template-literal strings, not a framework — there is no React/Vue/etc.). Procedural Web Audio (music + SFX) lives in `apps/web/src/engine/audio-engine.js`; real-accounts/classroom/submission/grading logic lives in `apps/web/src/repositories/` and `apps/web/src/engine/` (`auth-flows.js`, `evaluator-requests.js`, `evaluator-client.js`) — both imported by `main.js`.

An orphaned second implementation of the onboarding→field→case-player loop (`apps/web/src/features/*`, plus its two supporting dead stores `engine/content/author-content-store.js` / `engine/player/player-profile-store.js`) used to exist alongside `main.js` — six files total, never imported by it, containing two more dead Author Mode implementations on top of `main.js`'s own broken one. It was confirmed zero-risk (per `docs/architecture/ARCHITECTURE-REVIEW-AND-SIMPLIFICATION.md`) and deleted in a dead-code-removal pass — see `docs/migrations/DEAD-CODE-REMOVAL.md`. Don't recreate it; when extending gameplay, edit `main.js` directly unless deliberately doing modularization work.

**All seven authored units** (`content/unit-01-campaign.js` through `unit-07-campaign.js`) carry real, cited historical content across every case, plus per-unit Archive Challenges, and all seven are registered in `main.js`'s `UNITS` as of Phase 89C. Two conventions differ between them and are deliberate: Units 1–3's field records are real named documents, while **Units 4 through 7's are composite documents reconstructed from a documentary form** — a canal toll receipt, a Confederate impressment requisition, a land-office receiver's receipt, a ship's manifest page — because nobody standing on a towpath is carrying the Bank Veto. Each such citation says so in its own first sentence; the canonical documents live in `content/primary-source-library/` and feed the missions and Archive Challenges instead. See `docs/decision-log/0049-units-four-and-five.md`. **Unit 7 was registered for validation and deliberately absent from `main.js`'s `UNITS` between Phase 89 and Phase 89C** — because `activeFieldMap()` silently falls back to Unit 1's Caribbean for a unit it has no map for, so registering a field case early does not error, it lands the player on the wrong continent. That is the state Units 3–5 sat in until Phase 81F and Unit 6 until Phase 87; see `docs/decision-log/0075-unit-seven-exists-on-paper.md`. **Don't register a future unit's field case before its map exists.** The serverless AI-grading backend at `api/evaluate.js` + `api/_lib/rubrics.js` (a real Claude-Haiku HIPP/SAQ/LEQ/DBQ evaluator — it's why `@anthropic-ai/sdk` is a production dependency) was unwired from the frontend for a long time; **as of Phase 22 it is wired up**, called from `sourceReader()`'s "initial reading" and the Archive Review SAQ block via `apps/web/src/engine/evaluator-requests.js`/`evaluator-client.js`. It still only ever returns formative feedback, never a grade — a teacher enters the real grade via the new `gradingScreen()`.

### State and persistence

`apps/web/src/engine/chronicle-progress-store.js` defines `DEFAULT_PROGRESS` (current screen, unlocked/completed cases, per-case evidence, dialogue responses, exchange ledger, empire connections, review answers, quest responses, `submissions`, `lastSavedAt`, etc.) and reads/writes it to `localStorage` under the key `republic-builder.chronicle.unit-01.v2`. **As of Phase 22, `localStorage` is no longer the only copy of a signed-in student's save** — `apps/web/src/repositories/progress-repository.js` sits in front of the untouched `local-progress-repository.js`/`chronicle-progress-store.js` and debounce-pushes to a real Supabase backend in the background (no-op if signed out), with a `hydrateRemoteProgress()` step merging a remote copy in on sign-in (last-write-wins by `lastSavedAt`). `localStorage` remains the fast/offline-first path and the only copy for anyone not signed into a classroom. `main.js` accesses this via `loadProgress` / `saveProgress` / `resetProgress` / `hasSavedProgress` / `hydrateRemoteProgress` exported from `progress-repository.js`. `progress.currentScreen` plus `VALID_SCREENS` in `main.js` drive the screen-routing state machine — examples include `institute`, `field`, `archive`, `practice-check`, `join`, `login`, `teacher-dashboard`, `grading`, and many others (30+ screens total).

Real accounts/classrooms/submissions/grades now also live in Supabase (schema + RLS in `supabase/migrations/0001_init.sql`) — `profiles`, `classrooms`, `roster_slots`, `student_world_profiles` (the remote mirror of the `progress` blob above), `submissions`, `evaluations`, `manual_grades`, `content_overrides`. See `docs/architecture/session-reports/2026-07-18-real-teacher-mode-accounts-classrooms-grading.md` for the full design and what's still unverified against a real project.

### Engine vs. content boundary

The repo's stated architecture rule (from the decision log): **engine code never contains APUSH-specific facts.** In practice today this is still violated — case-ID literals (`"case-001"`) are hard-coded directly into movement/interaction-gating code in `main.js`, not merely into content files. Treat the clean separation described in older docs as aspirational for the current vertical slice, not yet fully realized. One of these was removed in Phase 70 and the way it went is the pattern to follow: `sourceAvailability()`'s `caseId === "case-001"` branch became a `requiresSourceId` field the record itself carries, paid for by the second consumer that needed the same gate rather than by a speculative cleanup. **When a second case needs behaviour a literal currently hard-codes for the first, make it data instead of adding a second literal.** Canonical folder intent (corrected against the actual repository — the old table here previously had the asset-tree row backwards):

| Thing                                          | Home                                                                                    |
| ---------------------------------------------- | --------------------------------------------------------------------------------------- |
| Reusable engine systems                        | `apps/web/src/engine/`                                                                  |
| Campaign/unit content actually used at runtime | `apps/web/src/content/` — `unit-01-` through `unit-05-campaign.js`, all real            |
| Images, maps, audio, icons                     | `apps/web/src/assets/` — 718 real files, referenced via `new URL(..., import.meta.url)` |
| JSON schemas                                   | `data/schemas/` (currently one example instance, not a real JSON Schema)                |
| Docs                                           | `docs/`                                                                                 |
| Build/import/validation scripts                | `scripts/`                                                                              |

The placeholder-scaffold root `assets/` tree and the orphaned `apps/web/src/features/` island named in older revisions of this table were deleted in a dead-code-removal pass — see `docs/migrations/DEAD-CODE-REMOVAL.md`.

There is also a **dormant, unread** JSON content pipeline under `content/campaigns/chronicle/units/unit-01/` (`campaign.json`, `unit.json`, `case.json`, `activities/*.json`, `assessments/*.json`) plus record templates in `content/library/`. `main.js` never imports from this tree (confirmed by import-graph trace). It represents a _fourth_ incompatible schema for the same Case 1.01 source content (alongside the live `unit-01-campaign.js` shape and two dead ones) — don't treat its presence as meaning it's wired up, and don't reconcile the schemas speculatively; that's tracked as future `ContentRegistry`/Zod work in `docs/architecture/PLATFORM-ARCHITECTURE-PROPOSAL.md`, not a current task.

### Author Mode and real Teacher Mode (Phase 22 — no longer a stub)

A development-only in-app panel (toggled via the chrome button, rendered by `authorPanel()` in `main.js`) lets a teacher edit two front-facing copy fields (unit title, central question) without touching layout, scoring, or progression logic — see `docs/decision-log/0003-author-mode-and-content-overrides.md` for the original intent. **This is real and working**, not a stub: edits persist via `apps/web/src/repositories/teacher-override-repository.js`, which falls back to a per-browser `local-teacher-override-store.js` for signed-out/local dev, or writes to a classroom-scoped `content_overrides` Supabase table once a real teacher/classroom is active (Phase 22). (An earlier revision of this file claimed the two content-edit inputs had no working event listener — that was fixed in an earlier phase and this file simply hadn't been updated; don't trust old staleness claims about this panel without checking `main.js` directly.)

Beyond Author Mode's content overrides, Chronicle now has real teacher-facing tooling: a teacher creates a classroom, provisions a student roster, reviews AI-evaluated submissions, and enters manual grades via the `teacher-dashboard`/`grading` screens (`main.js`) backed by a real, live Supabase project (accounts, classrooms, submissions, evaluations, manual grades — schema in `supabase/migrations/0001_init.sql`). See `docs/architecture/session-reports/2026-07-18-real-teacher-mode-accounts-classrooms-grading.md` for the original design and `ARCHITECTURE-QUICKREF.md`'s Phase 22–24 and Phase 38 entries for current status — all migrations through `0010` are applied and live-verified as of Phase 38. ## Terminology

Use these consistently in code, copy, and UI strings — they're the game's fixed internal vocabulary:

- **Chronicle Institute** — the organization; **Institute Archive** — the visible hub room/screen name (`chrome()`'s "Institute" branding + `HUB_TARGETS`/`institute` screen in `main.js`).
- **Entrance Hall** — the room the player arrives in and the first thing they control (Phase 63, decision log `0046`). One of **three** hub rooms, all on the `institute` screen and told apart by `progress.currentHubRoom` (`"main"` | `"archive"` | `"hallway"`), resolved through `activeHubGrid()`/`activeHubBlocks()`/`activeHubTargets()`/`activeHubNpcRuntime()`. There is no `intro-hallway` screen any more — it was retired along with the five-second scripted float that used to live on it; don't reintroduce a screen for a room. `hallway.tmj` is that room; `institute-hall.tmj` is the Main Hall.
- **Chronotravel** — traveling to a historical setting (the `travel` screen / "Initiate Chronotravel").
- **Chronotravel plate** — the painted establishing shot a warp screen loads on, one per destination (`content/chronotravel-plates.js`, art in `assets/plates/`). **Keyed by unit, not by case**: a unit is one place and one era, so Unit 1's three cases all open on the 1493 Caribbean whether they route to a field map or not. Everything else on the card comes from the case and the unit, so a renamed mission renames its own loading screen. A plate's `note` is **flavour and must stay flavour** — it is the one screen with a player's whole attention and no task on it, which is the reason to refuse the temptation to teach through it. Units 7–9's plates were painted and committed **unwired**, so a new unit is one table line — Unit 7 collected its line in Phase 89 and cost exactly that; Units 8 and 9 are still queued. `tests/unit/chronotravel-plates.test.js` fails if a shipped unit has no plate, if the table names a unit that does not exist, or if one of the two remaining queued files is deleted as "unused". Build them with `npm run assets:build-plates` — sources live in a gitignored `art-source/plates/`, out of `assets/` so nothing can reference the 2.5 MB PNG by accident.
- **Warp screen** — the two transitions, built by one function (`warpScreen()` in `main.js`, Phase 88A/88B, decision logs `0073` and `0074`): `travel` out and `return-warp` back, differing only in which plate they load, which way the streaks and anchor rings run, and three strings. Full-bleed and **chrome-less**, like the title sequence. **Two beats and three phases on one render**, flipped on `data-warp-phase` by `beginWarp()`: `tunnel` (a canvas streak field over `WARP_TUNNEL_MS`, its own bottom bar, the destination card resolving out of blur), `plate` (the painting settles, a ring fills 0%→100% over `WARP_DWELL_MS`) and `ready` (the ring reads "Synced" and the arrival prompt appears). ## Gameplay invariants (regression-prone areas)

These patterns recurred as bugs across many hotfix milestones (3.4.5 through 3.4.15 in the decision log) — be deliberate when touching this code, and visually re-test rather than trusting a syntax check.

- **Camera must stay a pure function of player position.** `updateFieldPlayer()` / the hub equivalent recompute `fieldCamera`/hub transform every tick from `fieldMovement.x/y` (clamped to viewport bounds, integer-rounded to avoid blurry text). Don't introduce `scrollIntoView()`, `.focus()`-triggered scrolling, or click-handlers that move the camera toward a clicked DOM element — several past regressions came from exactly that.
- **Proximity-gated interaction.** NPCs/objects only become interactable within a reach radius (see `targetDistance`/`targetReach`/`nearestHubTarget` for the hub, and the analogous field logic) — both `E` keypress and click should require the player already be in range, not act as a teleport-and-interact.
- **One interaction prompt at a time**, cleared when dialogue closes, the player moves out of range, the screen changes, or progress resets — watch for stale "Press E" prompts or duplicate prompts after refactors. **The field's equivalent is `#fieldNotice`, and it is a status line rather than a prompt** — the field has no "Press E" surface at all (`.field-interact-prompt` was swept as dead CSS in Phase 45D; a marker's own label appearing on approach is what names it). It is written only by `fieldTooFarNotice()` and `refuseLockedRecord()`, and until Phase 90E nothing ever took it back: it cleared on arrivals and not on the player doing what it asked, so "Move closer to interact with Taíno canoe worker." survived the walk to a different NPC, that whole conversation, and every record read after it. **An attempt that lands clears the line left by one that missed** — that is `toggleFieldDialogue()` / `openFieldRecord()` / `beginFieldRecord()`, and a fourth writer of this line has to clear it too.
- **Dialogue renders anchored to the speaking NPC**, in a layer that doesn't force the world transform to reset or the document to scroll. The bubble is a flex column whose content lives in `.field-speech-bubble__scroll` — anything added to it goes inside that child or it will not scroll — and `placeFieldDialogueBubble()` puts it on whichever side of the speaker has more room, caps it to that room, and lets the rest scroll. **Check the cascade before the arithmetic here.** Two rules in this area were dead for a full phase and neither failed loudly: `--below`'s flip lost to a `transform: … !important` restated further down `global.css`, and `:has(.field-interview) { width: 404px }` lost to the base rule's `max-width`. Both were found by measuring in the browser, not by reading the file (decision log `0052`).
- **A per-frame path patches the DOM; it does not render.** `updateFieldNpcs()` and `updateFieldProximityUi()` say so, and Phase 90E paid to learn it applies to state changes too. Walking away from a conversation clears `activeFieldNpc`, and the bubble that state drew has to go with it — but making the movement loop `render()` (what every deliberate exit does) repaints the map canvases on the frame a player starts walking, and turned **four unrelated e2e specs red under parallel workers while they stayed green at `--workers=1`**. `closeFieldDialogueOnMove()` removes the one node instead. The general lesson is worth more than the fix: **an e2e suite can only report a performance regression as a correctness failure**, so several specs failing at once in an area nobody touched is one cause, not several flakes.
- **NPC movement respects the same collision as the player** (`FIELD_BLOCKS`/`HUB_BLOCK_RECTS`, land checks via `isCaribbeanLand`) and swaps sprite sheets by facing direction rather than sliding a front-facing sprite sideways. Since Phase 60 that means four real directions — `down`/`up`/`left`/`right`, each its own horizontal walk strip on the shared 48×56 canvas (`engine/sprite-animation.js`, `CHARACTER_SHEETS` in `main.js`). There is no mirroring and no `side` sheet: `up` used to be the south sprite tinted darker and `left` used to be east flipped, and both are real art now. Column 0 of every strip is a standing pose for that direction, which is how a character keeps facing the way it last walked. **The 48×56 canvas is pinned, not derived** (Phase 64): `canonicalCanvas()` in `scripts/assets/build-character-sheets.js` clamps to `SPRITE_CANVAS` rather than sizing itself from the widest cast member, so adding a character with a long prop clips that prop instead of silently resizing all 140 committed PNGs and invalidating the CSS tokens and visual baselines with them. Change `SPRITE_CANVAS` deliberately if the canvas must ever move; don't let a new character decide it.
- **An NPC has a job** (Phase 62, decision log `0045`). `FIELD_NPC_BEHAVIOURS`/`UNIT2_*`/`UNIT3_*`/`HUB_NPC_BEHAVIOURS` map an id to one of three kinds, defined in `engine/npc-behaviour.js`: `station` (stands at `at`, turns to look around), `route` (walks a circuit of `stops`), `wander` (a disc around `home`, Phase 61's behaviour). All seeded per NPC id, so a character behaves the same way across reloads.
  - **A route is authored as places, not waypoints.** `engine/npc-routing.js` pathfinds between consecutive stops over the map's walkable cells, costing a road cell a quarter of open ground so people use the road; road cells come from the generators as `*_ROADS` in `<map>.blocks.js`. Don't hand-write intermediate waypoints — name the two or three places the person has business being.
  - **Authoring cannot strand anyone.** A stop snaps to the nearest open cell, an unpathable leg is dropped, a route left with nothing degrades to a station, and every step is still gated by `isFieldNpcBlocked`/`isHubNpcBlocked`. `tests/unit/field-map-coordinates.test.js` fails if a shipped route never reaches a stop.
  - **Two people must not share ground.** `nearestFieldInteraction()` answers with whoever is closest, so a player who walked to one gets the other. This shipped twice — the Powhatan pair by overlapping wander discs, the burgess by a _route whose path_ ran 1.1 tiles from the stationed minister while its stops were a comfortable 2.9 away. The coordinate test measures a route's whole walked path, not its stops, against a 1.5-tile bar (just above the 1.45 interaction reach).
  - **A person and a piece of furniture must not share ground either** (Phase 90C, decision log `0080`). The doorstep-NPC hazard above is one instance of a general rule, and the Institute had the other: Prof. Park's route stopped 1.4 tiles from the Navigation Table, inside its 1.65 reach, so `E` at the table opened the professor. Two things were wrong and both had to be fixed — `nearestHubTarget()` was `Array#find`, so despite its name it answered in **`HUB_TARGETS` declaration order** rather than by distance (it is `nearestInReach()` now, exported and unit-tested), and a body parked in the room's one approach is still wrong with the sort fixed. Post staff two and a half tiles clear of an interactable object; `field-map-coordinates.test.js` now asserts it for the Main Hall. **The seven field maps are swept too as of Phase 90E**, at a different bar and deliberately: each target's own reach (1.55 for an object-anchored record, 1.45 for a door), not 2.5 — because 2.5 is right for a room whose one approach is a doorway and wrong for a market square, where a notice board is meant to have people walk past it. It measures `territoryOf()`'s **walked path**, which is the only thing that catches this: Philadelphia's town crier came 1.39 tiles from the Assembly hall notice board while his stops sat a comfortable 1.98 away, so mid-stride the broadside opened the crier. **Only `E` ever went through that sort** — `handleHubClick`'s `hub-interact` passes `dataset.target` straight through — which is why a mouse never reproduced it and it survived for many phases behind a workaround button in Julian's own dialogue.
- **`E` and a click must reach the same thing the same way, and when they don't it is the keyboard that is wrong.** This has now shipped twice and **both times the pointer path was the correct one**, so neither bug is reachable by anyone testing with a mouse. Phase 90C: `nearestHubTarget()` sorted by declaration order while `hub-interact` passed its id straight through. Phase 90D (decision log `0082`): `nearestFieldInteraction()` offered a record whose marker `fieldSourceSignal()` deliberately does not draw — a locked one — so the gate the click path could never reach was the only gate in the game, and **Richmond's price board opened**. The rule that falls out: **when a control exists in two forms, the state changes live in one function both call.** `nearestInReach()`, and `openFieldRecord()`/`beginFieldRecord()`, are that shape. A third path into a record must go through those two, and a record's availability is `sourceAvailability()`'s answer, asked by `refuseLockedRecord()` and nowhere else — **do not add a case-id literal beside it**, which is the half of Phase 70's fix that got left behind for five more units. `tests/unit/field-record-gate.test.js` fails if either literal returns or a third entry point appears. **`toggleFieldDialogue()` is the third of these** (Phase 90E, decision log `0083`) — `E` and a click carried character-for-character copies of the dialogue toggle, caught before they drifted rather than after. **That rule has a dual, and both are worth carrying because different habits catch them** (Phase 90H, decision log `0086`): **when one variable answers two questions, the second question gets the first one's answer.** `sourceOrigin` said both where the reader goes back to and where the Codex goes back to, so opening a record from the Codex destroyed the Codex's memory of the Institute and its "← Return" fell through to the field — five ordinary presses from the Archive Room's own side panel. The duplication rule is found by diffing two call sites; this one cannot be, since there is one assignment and one read and each is locally correct. It is found by asking what a name means, and `origin` does not say origin _of what_. `codexOrigin` is the second variable; a third reader of either belongs to whichever question it is asking.
- **A door is an interaction, and it competes for the same reach.** A field interior's door is a third kind in `nearestFieldInteraction()` alongside `npc` and `source`, at the same 1.45-tile radius and in the same nearest-wins sort — walking over a threshold does nothing. The cost lands in authoring: **post a doorstep NPC two and a half tiles clear of the door**, or the person wins the sort and the room becomes unreachable from every approach. That has now shipped twice — Canal Crossroads' editor a tenth of a tile from his own shop's threshold, and Unit 6's register and telegraph operator four tenths and half a tile from theirs, which would have left both Cottonwood Junction rooms unenterable. **Nothing in the suite catches this**: the conflict is between a door and an NPC, and `field-map-coordinates.test.js` measures NPC against NPC. Check a new interior's door cell against the outdoor cast by hand.
  - **An interior must be attached after the `FIELD_MAPS` literal, not inside it.** A room's `blocks` const is declared further down `main.js`, and reading one from inside the literal is a temporal-dead-zone `ReferenceError` that takes the app down on boot.
  - **Every field surface must declare `isLand`**, or `map.isLand is not a function` throws on the first movement frame. Interiors use the shared `interiorGround(grid)` factory — a plain in-bounds test, because a room's walls are collision rects, not a coastline.
  - **A room smaller than its frame centres; it does not clamp.** The outdoor follow-and-clamp formula degenerates to a top-left pin once the world stops being bigger than the viewport. This is still a pure function of player position — for a small room it is a constant one, so the camera invariant holds.
  - **A record draws only on its own surface; the checklist lists them all.** A case's `sources` is the whole case's list everywhere, so `fieldSourceSignal()` guards per-surface — without it, records from elsewhere stack on `sourcePointPosition()`'s (10,10) fallback in the middle of the room. The **Mission Tracker** is deliberately the opposite and resolves anchors across _every_ surface of the unit's map, because it is the only thing that says there is anything behind a door at all.
- **Nothing in the game looks at where a character's name pill lands.** `--cast-label-top` hangs it a fixed distance below the feet, so any `base`-solidity object whose overlay row a character can stand on will draw over the label — Unit 6's land office cut the register's name in half with its own counter rail. Five of the eight interiors now have such objects, and Unit 7's inspection hall has two — its rails are stamped `base`, so anyone posted within about 1.6 tiles of the row above one loses their name to it. There is no test for it and there should not be a clever one; look at the room.
- **A new field map costs a `FIELD_COPY` entry, and forgetting one is silent.** `fieldScreen()` falls back to Unit 1's briefing when a map has no entry of its own, so a map that skips it tells its player to "follow the shoreline toward the Spanish camp." Unit 6 shipped with exactly that and it took a browser to see it; `tests/unit/field-map-coordinates.test.js` now asserts one entry per `FIELD_MAPS` key, reading `main.js` as source because the table is not exported.
- **A sequencing quest must be authored out of order.** `renderSequencingQuest()` lays items out in the authored array's order and never shuffles, so `items` written `position: 0,1,2,3,4,5` render already solved and grade the student correct for touching nothing. Keep each item's `position` right and its place in the array wrong. This is a **failing test** as of Phase 81F rather than a convention — `tests/unit/sequencing-quest-order.test.js` sweeps every unit's sequencing arrays through `loadChronicleContent()`, so a sixth unit is covered the moment its arrays are registered. It went five-for-five as prose alone.
- **A scripted beat moves characters, never the screen** (Phase 63, decision log `0046`). Every scene works by writing to the same objects the ordinary loops already read — an NPC's own behaviour state and `instituteMovement` itself. That is what keeps the camera a pure function of player position with no new code path, and it is why `engine/cutscene.js` has **no camera command and never will**; if you add a scripted moment, move the bodies. `engine/escort-walk.js` is a pure primitive (leader walks a `findRoute()` path, follower samples that trail a fixed distance behind, needing no collision test of its own because the leader has already walked every point of it). **There is now one scripted-scene code path, not two** — Phase 81G folded the Entrance Hall's bespoke `hallwayScene` onto the `engine/cutscene.js` interpreter, so a scene is a list of commands in `content/cutscenes.js` and `main.js` hosts it. **A scene that needs something the eight commands cannot say wants an `onDone`, not a ninth command**: `startHubScene(id, { onDone })` is how the Entrance Hall changes rooms when it ends, because where the screen goes next is host state and a content file has no business naming it.
- **One input lock, `isHubInputLocked()`.** Every scripted beat suspends player control through that one predicate, checked at the same three sites — the institute keydown branch, `runHubMovementLoop()`, and `interactWithHubTarget()`. Adding a second lock concept checked at an overlapping subset of those is how a screen ends up controllable during half of a cutscene. Anything that locks movement must also suppress the "Press E" prompt, or it hangs there offering an interaction that is already happening. It was three terms, then two, and is **one** as of Phase 90 — `isHubSceneActive()` — because the Main Hall's tutorial tour stopped being a caption panel with its own lock and became `director-tour`, a scene like any other. Keep the function anyway; a bare predicate at three call sites is what stops a second one appearing beside it.
- **Ground speed drives the walk cycle, per body, per moment.** `updateInstitutePlayer(speed)` takes the player's _current_ speed rather than assuming `HUB_SPEED` (3.65): a scripted walk travels at `SCENE_WALK_SPEED` (2.2), and passing the default there would run their legs 66% faster than their feet. Same rule as `walkCycleSeconds()` everywhere else — if something moves a character at a speed that isn't the usual one, it has to say so. **A second loop writing the same sprite is the same bug wearing a hat**: the 30Hz `updateInstituteNpcs()` interval used to run straight through scenes, repainting the player at the default speed ~30×/s while the scene's own frame painted it at the scripted one, so the walk cycle stuttered between 0.301s and 0.5s. It stands down while `isHubSceneActive()`.
- **A follower ends a walk a gap behind the leader, never on top of them** (`engine/escort-walk.js`, Phase 90). Two related things are easy to get wrong here and both shipped: the trail is seeded from the **follower's** own position at negative arc length, or the follower teleports onto the leader's path the first frame it engages; and `snapActor()` in the scene runner has to move the follower too, reading `command.follower` rather than `hubScene.followsPlayer` — skip never runs `moveActor`, so that field is stale by definition. Both were invisible until a second scene used a follower.
  - **A stationed NPC is furniture to everyone else.** Their posts go into `createNavGrid`'s `occupied` list, or a route planned through one leaves that person blocked against them for good.
- **Four numbers tie the cast to the world, and none of them should be eyeballed.** `--cast-h: 56px` renders the 48×56 canvas 1:1 against 48px tilesets — don't reintroduce a per-viewport override, since fractional scaling is what it exists to remove. `--cast-foot` is a world offset scaled by `--tile`, and its value per surface is that surface's collision foot-box centre (`FOOT_ANCHOR` in `engine/sprite-animation.js`); when it drifted from that, the Institute drew everyone a full tile below where collision held them. `--cast-label-top` hangs a character's name pill a fixed distance below `--cast-foot`, so one expression puts it under the feet on both surfaces; written against the button's own box instead, it tracked the hit area, and the field's pill sat across everyone's boots through six re-tunings. Walk-cycle duration comes from ground speed through `walkCycleSeconds()`, never a fixed value — a hard-coded cycle is what made the player glide and the NPCs skate.

## Visual design language

- Palette (see CSS custom properties in `apps/web/src/styles/global.css`): deep navy (`--navy`), gold (`--gold`, `--gold-soft`), warm parchment/ink (`--paper`, `--ink`), muted teal accents. Keep new UI within this blue/gold/bronze/parchment historical-adventure look, not a generic admin-panel style.
- A custom bronze/gold ornate arrow cursor is already implemented as an inline SVG data URI in `global.css` — reuse/extend it rather than reverting to the system cursor for in-game surfaces.
- Don't cluster interactive elements together while leaving large map areas empty — placement should be diegetic (e.g. cartographer table near the ship, canoe worker near shore) and UI chrome (status panels, prompts) should sit outside the playable floor rather than overlapping NPCs, furniture, or pathways.

## Persistence

`chronicle-progress-store.js` (key `republic-builder.chronicle.unit-01.v2`) is still the base layer: a single flat `localStorage` blob, and the only save state for anyone not signed into a real classroom. **As of Phase 22, this is no longer the only copy for a signed-in student**: a real Supabase backend now exists (accounts, classrooms, submissions, evaluations, manual grades, classroom-scoped content overrides — schema in `supabase/migrations/0001_init.sql`), and `apps/web/src/repositories/progress-repository.js` layers background sync on top of the untouched local store — exactly the "small service/adapter in front of a versioned save schema" this section used to describe as future design intent. When adding new persisted fields, still extend `DEFAULT_PROGRESS` and the merge logic in `readProgress()` — that pattern is unchanged, just now also mirrored to `student_world_profiles` in Supabase. See `docs/architecture/session-reports/2026-07-18-real-teacher-mode-accounts-classrooms-grading.md` for the full design and what's still unverified against a live project.

## Development workflow expectations

- Prefer small, focused changes over broad refactors; don't fix unrelated things in the same pass.
- Avoid modifying `vite.config.js` unless the task genuinely requires it.
- Compilation/syntax passing is not sufficient to call something fixed — this is a visual/interactive game. Verify using the ladder below before considering a change done. Don't commit until the requested behavior has actually been tested.
- **No `/verify` skill exists in this repo** — an earlier revision of this file referenced one; don't look for it or invent an ad hoc equivalent. The verification ladder below is the actual expectation.

### Verification ladder (cheapest first — escalate only as needed)

Run the cheapest check that actually exercises what you changed; stop once you've cleared the tier that matters for this change. Don't jump straight to a manual/MCP browser pass by default — it is the _most_ expensive tier, not the default one.

1. **Targeted `vitest`**, scoped to the changed file/pattern: `npx vitest run tests/unit/<file>.test.js`, not a bare `npm run test`.
2. **`npm run validate:content`** — only if content files changed (schemas, `unit-0N-campaign.js`, `content/quests/*`).
3. **`npm run test:e2e`** — the real, committed Playwright suite (`tests/e2e/*.spec.js`, 35 spec files / 174 tests, added Phase 29). This is the default way to verify a player-visible interaction — run it before reaching for a manual browser pass, not after. For a CSS-only change, run `npm run test:e2e -- visual-regression` specifically: it screenshots every gameplay screen at 1366×768 against 51 committed baselines and will show you a pixel diff if anything moved. **It is not a check on cast art** — every screenshot containing a character hides `.hub-npc`/`[data-npc]` first, because NPCs animate on a rAF loop and are never pixel-stable, so a new or re-drawn sprite moves nothing here and must be verified by `character-sheet-geometry.test.js` and by eye. **Review a changed baseline before accepting it** — open the `-diff.png` and confirm every difference is one you intended; a blind `--update-snapshots` turns the whole suite into a rubber stamp.
4. **Full `npm run test` / `npm run lint` / `npm run build`** — at milestone boundaries or when the change touches shared infrastructure (a screen-routing guard, a repository facade, a quest-type contract all four types implement).
5. **A manual browser pass (`npm run dev`, by hand or via an MCP browser tool)** — only for an interaction genuinely uncovered by any committed spec. When you do this, **bank it**: add the scenario as a new `tests/e2e/*.spec.js` file (or a case in an existing one) so the next session doesn't re-derive it by hand. A manual pass that isn't banked is cost paid twice for the same coverage.

### The Spine Review — the standing part-by-part playtest program

`docs/playtest/PLAYTHROUGH-LEDGER.md` is the single source of program state: an ordered walk of the **student** experience, intro through unit completion, in thirteen parts. Read the ledger before starting a review part or acting on a defect report about a player-facing screen — a finding may already be recorded and routed. Each part gets its own `part-NN-*.md` **when it starts**, never before; the ledger holds status and counts and never finding text. The protocol and the severity/category taxonomy live in the ledger, in one place, deliberately.

**Parts 0 through 9 are closed as of Phase 90H**, which is the whole of the strictly-ordered spine; 10, 11 and 12 branch off it and are reorderable, so the program no longer names its own next row. Two rules from it that bind any session touching the program: **an S3 finding must name a destination** (a part number, the content queue, or an ADR), and **a part's ledger row is updated in the same commit as its fix** — if the row isn't in the diff, the part isn't closed. The program fixes behaviour, never shape: no restructuring, no new systems, no new content. Teacher surfaces are deliberately out of scope.

`?warp=<name>` (dev only, `DEV_WARPS` in `main.js`) boots straight into a named save state so a review pass starts where it starts — `intro`, `hall`, `hub`, `table`, `field`, `mission`, `railhead`, `port`, `reveal`. It is gated on `import.meta.env.DEV` and verified absent from production builds; adding a state is one line in that table.
