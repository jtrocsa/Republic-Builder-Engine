# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The current game is **Chronicle**, an AP U.S. History RPG: a browser-based, top-down field/dialogue game. It covers **CED Periods 1–8 of 9** as of Phase 97 — twenty-four cases across eight units, all with real, cited historical content, on eight walkable outdoor field maps plus ten interiors. **Unit 9's content shipped in Phase 100** and is registered for validation but deliberately not playable, so the repository holds nine units of content and the game a student can walk is eight. Unit 1 "The Atlantic World" (case-001–003), Unit 2 "Colonial Crossroads" (case-004–006), Unit 3 "Revolution and Founding" (case-007–009), Unit 4 "Democracy, Markets, and Reform" (case-010–012), Unit 5 "A House Divided" (case-013–015), Unit 6 "A Continent on Paper" (case-016–018), Unit 7 "The Terms of Belonging" (case-019–021), Unit 8 "Grounds for Refusal" (case-022–024). **Units 1–6 reached parity in Phase 87** — Unit 6's map shipped in Phase 85, its two interiors in Phase 86 and its three activities in Phase 87. **Unit 6 is complete as of Phase 88**, when its Meridian reveal shipped — the last thing it was owed. **Unit 7 became playable in Phase 89C**, when its wharf at Ellis Island shipped and the `UNITS` line was added — so the game a student can walk is now Periods 1–7 — its two interiors shipped in Phase 89D, and **its three missions shipped in Phase 89E, which completes it**. **All eight units are at parity**: every one has a walkable map, its interiors, and three playable missions on it — twenty-four missions in all. **Unit 8 became walkable in Phase 97**, its two interiors shipped in Phase 98 and its three missions in Phase 99, which completes it. Four of Unit 7's seven records keep `activityRoute: null` and open in the reader, which is what every non-mission record on the other six maps does — three missions is the slate, and seven activities would be a different design. See `docs/decision-log/0081-three-missions-at-the-immigrant-station.md`. Unit 8 was built in the documented order — content (Phase 95), art (96), map and cast (97), interiors (98), activities (99) — end to end without a variation worth recording, which is the order **Unit 9 is now following**: its content shipped as Phase 100 (`0099`), and it owes art reconnaissance, a map and cast, two interiors and three activities. See `docs/decision-log/0094-the-word-is-not-on-the-form.md` through `0099`.

**"Republic Builder Engine" is retired as the project's identity, and as of Phase 81 the string is gone from every rendered surface.** The repository was originally framed as a reusable engine of that name; that framing is no longer current. The eventual multi-subject platform this codebase may grow into **does not yet have a final name** — don't invent one or reintroduce "Republic Builder" branding in new code, docs, or copy. `BRAND.engine` no longer exists (removed from the content file, `BrandSchema`, and its ten render sites), the chrome header is now a one-line lockup, and the tab title, `package.json` name and README front matter all say Chronicle. Two survivals are deliberate: the `localStorage` key `republic-builder.chronicle.unit-01.v2`, because renaming it orphans every existing save, and the repository folder name itself. **Don't "finish the job" on either.**

**Removed systems — do not restore:** Founder Paths, professions, Historian Skills, and clothing/wardrobe-slot systems have been removed from the design and must not be reintroduced. The player identity model is intentionally minimal (display name + one of two appearance choices only — see `docs/decision-log/0005-chronicle-identity-and-first-field-entry.md`); pronouns, wardrobes, professions, cosmetics, and inventory remain deliberately out of scope, not merely deferred to a later milestone.

### Product intent

The goal is a Pokémon-inspired APUSH RPG students use across a full school year — approachable controls, a stylized explorable world, NPC dialogue bubbles, independent NPC movement, location-specific music, and badge/collection progression — not a quiz site or worksheet reskin. Gameplay is meant to train authentic AP U.S. History skills (HIPP source analysis, SAQ/LEQ/DBQ argument construction, evidence-based reasoning) using real primary sources and the actual College Board rubrics where applicable, rather than relying on trivia recall. Game progression must never grant unfair advantages on graded assessments — cosmetic rewards, organizers, and alternate routes are fine; pay-to-win or build-to-win mechanics on assessments are not.

Narrative frame: the player is recruited at the Chronicle Institute (present day) because the historical record has become damaged/unstable, becomes a "Chronicler," and uses "Chronotravel" to visit historical settings, gather evidence from people and primary sources, and transmit/preserve records back at the Institute Archive to earn area badges. Historical dialogue may take reasonable dramatic liberties but should stay in the speaking character's voice — avoid fourth-wall commentary, repeated "this is dramatized" disclaimers inside conversations, or modern educational narration coming out of a historical figure's mouth.

## Commands

Run from the repo root (npm scripts shell out to Vite, which is rooted at `apps/web` via `vite.config.js`):

- `npm run dev` — start the Vite dev server (opens the browser automatically)
- `npm run build` — production build (output in `apps/web/dist/`)
- `npm run preview` — preview a production build
- `npm run validate:content` — real, working Zod-based validator (run `npm run docs:stats` for the current group count). Validates every registered unit's `unit-0N-campaign.js` and `quests/unit-0N-quests.js` against schemas in `apps/web/src/content/schemas/`, plus the 9-unit primary source library, and checks global case/source id-uniqueness, per-quest-type id-uniqueness, case-period-matches-unit, and every archive/investigation/reader/alternate challenge cross-reference. **Its per-unit blocks are derived, not hand-written** (Phase 90J) — `apps/web/src/content/unit-registry.js` holds `UNIT_IDS`, and adding a unit costs one line there plus its imports and one line in `local-content-repository.js`'s `UNIT_MODULES` — **plus a Chronotravel plate and a Navigation Table view**, each of which has a test that fails without it. **One block was still hand-written until Phase 100 and it cost a unit a phase of checking**: `checkActivityRoutes()` iterated `["unit01" … "unit07"]`, so Unit 8's three activities were never cross-checked against its routed sources — and the thing it would have caught was real, because `UNIT_MODULES` still carried that unit's `activities: {}` placeholder. See `docs/decision-log/0099-the-validator-stopped-at-unit-seven.md`. See `0094` §5 for the measured cost, and note that a unit with content but no map must not be handed to `build-field-guide.js`, which documents maps. A content export the validator has no schema for is a **hard error**, not a skip. See `docs/content/CONTENT-VALIDATION.md`.
- `npm run lint` — real, working ESLint flat config (`eslint.config.js`)
- `npm run format` / `npm run format:check` — real, working Prettier

A test runner **is** configured: `npm run test` (Vitest, non-watch, CI-compatible) runs tests from `tests/unit/` — see `docs/development/UNIT-TESTING.md`. ESLint and Prettier **are** configured and working — don't claim otherwise.

Type checking is **editor-only and advisory**, not a gate. `jsconfig.json` turns on `checkJs` for `apps/web/src/engine/**` and `apps/web/src/repositories/**` only — everything else, `main.js` included, is unchecked. There is no `npm run typecheck` script and TypeScript is not a dependency; measure it on demand with `npx -y -p typescript tsc -p jsconfig.json --noEmit`. The current baseline is **16 errors, all verified false positives** (untyped `supabase-js` embeds inferring `{}`/arrays, `number[]` where a `[x, y]` tuple is wanted, and Safari's `webkitAudioContext`) — so treat a _new_ error as worth reading, but don't "fix" the standing 16 by changing engine code.

Spell checking is configured in `cspell.json`, with word lists in `.cspell/` — `project-words.txt` (domain/engine/tooling vocabulary) and `source-quotations.txt` (period spellings quoted verbatim from primary sources, which must **not** be "corrected"). The repo is calibrated to zero unknown words, so any hit is a real typo. Check with `npx -y cspell "<glob>"`. Note that `19th Centruy European Dock`, `Labratory`, and `Jamestown Capenter` are misspelled _upstream_ — on disk and in PixelLab respectively — so those strings are correct in code and must stay.

## Architecture

### The app is currently one file

The entire running game is implemented in **`apps/web/src/main.js`** (16,427 lines as of Phase 94 / 2026-08-27 — re-check the line count with a quick `wc -l` before citing it if much time has passed, don't trust a stale figure, and use `wc -l` rather than PowerShell's `Measure-Object -Line`, which under-reports this file by ~340 — this file has grown substantially phase over phase and old figures go stale fast). It owns: screen routing/state machine, field and hub movement/collision/NPC patrol logic, dialogue, the activity host screen, the exchange ledger, the Author Mode panel, quest rendering/grading, the join/login/teacher-dashboard/grading/manage-content screens, and all HTML rendering (via template-literal strings, not a framework — there is no React/Vue/etc.). Procedural Web Audio (music + SFX) lives in `apps/web/src/engine/audio-engine.js`; real-accounts/classroom/submission/grading logic lives in `apps/web/src/repositories/` and `apps/web/src/engine/` (`auth-flows.js`, `evaluator-requests.js`, `evaluator-client.js`) — both imported by `main.js`.

An orphaned second implementation of the onboarding→field→case-player loop (`apps/web/src/features/*`, plus its two supporting dead stores `engine/content/author-content-store.js` / `engine/player/player-profile-store.js`) used to exist alongside `main.js` — six files total, never imported by it, containing two more dead Author Mode implementations on top of `main.js`'s own broken one. It was confirmed zero-risk (per `docs/architecture/ARCHITECTURE-REVIEW-AND-SIMPLIFICATION.md`) and deleted in a dead-code-removal pass — see `docs/migrations/DEAD-CODE-REMOVAL.md`. Don't recreate it; when extending gameplay, edit `main.js` directly unless deliberately doing modularization work.

**All eight authored units** (`content/unit-01-campaign.js` through `unit-08-campaign.js`) carry real, cited historical content across every case, plus per-unit Archive Challenges, and **all eight are registered in `main.js`'s `UNITS`** as of Phase 97. Two conventions differ between them and are deliberate: Units 1–3's field records are real named documents, while **Units 4 through 8's are composite documents reconstructed from a documentary form** — a canal toll receipt, a Confederate impressment requisition, a land-office receiver's receipt, a ship's manifest page, a recorded deed with a restrictive covenant — because nobody standing on a towpath is carrying the Bank Veto. Each such citation says so in its own first sentence; the canonical documents live in `content/primary-source-library/` and feed the missions and Archive Challenges instead. See `docs/decision-log/0049-units-four-and-five.md`. **Unit 7 was registered for validation and deliberately absent from `main.js`'s `UNITS` between Phase 89 and Phase 89C** — because `activeFieldMap()` silently falls back to Unit 1's Caribbean for a unit it has no map for, so registering a field case early does not error, it lands the player on the wrong continent. That is the state Units 3–5 sat in until Phase 81F, Unit 6 until Phase 87, and Unit 8 from Phase 95 to 97; see `docs/decision-log/0075-unit-seven-exists-on-paper.md` and `0094`. **Don't register a future unit's field case before its map exists.** The serverless AI-grading backend at `api/evaluate.js` + `api/_lib/rubrics.js` (a real Claude-Haiku HIPP/SAQ/LEQ/DBQ evaluator — it's why `@anthropic-ai/sdk` is a production dependency) was unwired from the frontend for a long time; **as of Phase 22 it is wired up**, called from `sourceReader()`'s "initial reading" and the Archive Review SAQ block via `apps/web/src/engine/evaluator-requests.js`/`evaluator-client.js`. It still only ever returns formative feedback, never a grade — a teacher enters the real grade via the new `gradingScreen()`.

### State and persistence

`apps/web/src/engine/chronicle-progress-store.js` defines `DEFAULT_PROGRESS` (current screen, unlocked/completed cases, per-case evidence, dialogue responses, exchange ledger, empire connections, review answers, quest responses, `submissions`, `lastSavedAt`, etc.) and reads/writes it to `localStorage` under the key `republic-builder.chronicle.unit-01.v2`. **As of Phase 22, `localStorage` is no longer the only copy of a signed-in student's save** — `apps/web/src/repositories/progress-repository.js` sits in front of the untouched `local-progress-repository.js`/`chronicle-progress-store.js` and debounce-pushes to a real Supabase backend in the background (no-op if signed out), with a `hydrateRemoteProgress()` step merging a remote copy in on sign-in (last-write-wins by `lastSavedAt`). `localStorage` remains the fast/offline-first path and the only copy for anyone not signed into a classroom. `main.js` accesses this via `loadProgress` / `saveProgress` / `resetProgress` / `hasSavedProgress` / `hydrateRemoteProgress` exported from `progress-repository.js`. `progress.currentScreen` plus `VALID_SCREENS` in `main.js` drive the screen-routing state machine — examples include `institute`, `field`, `archive`, `practice-check`, `join`, `login`, `teacher-dashboard`, `grading`, and many others (30+ screens total).

Real accounts/classrooms/submissions/grades now also live in Supabase (schema + RLS in `supabase/migrations/0001_init.sql`) — `profiles`, `classrooms`, `roster_slots`, `student_world_profiles` (the remote mirror of the `progress` blob above), `submissions`, `evaluations`, `manual_grades`, `content_overrides`. See `docs/architecture/session-reports/2026-07-18-real-teacher-mode-accounts-classrooms-grading.md` for the full design and what's still unverified against a real project.

### Engine vs. content boundary

The repo's stated architecture rule (from the decision log): **engine code never contains APUSH-specific facts.** In practice today this is still violated — case-ID literals (`"case-001"`) are hard-coded directly into movement/interaction-gating code in `main.js`, not merely into content files. Treat the clean separation described in older docs as aspirational for the current vertical slice, not yet fully realized. One of these was removed in Phase 70 and the way it went is the pattern to follow: `sourceAvailability()`'s `caseId === "case-001"` branch became a `requiresSourceId` field the record itself carries, paid for by the second consumer that needed the same gate rather than by a speculative cleanup. **When a second case needs behaviour a literal currently hard-codes for the first, make it data instead of adding a second literal.** Canonical folder intent (corrected against the actual repository — the old table here previously had the asset-tree row backwards):

| Thing                                          | Home                                                                                                      |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Reusable engine systems                        | `apps/web/src/engine/`                                                                                    |
| Campaign/unit content actually used at runtime | `apps/web/src/content/` — `unit-01-` through `unit-05-campaign.js`, all real                              |
| Images, maps, audio, icons                     | `apps/web/src/assets/` — referenced via `new URL(..., import.meta.url)`; `npm run docs:stats` counts them |
| JSON schemas                                   | `data/schemas/` (currently one example instance, not a real JSON Schema)                                  |
| Docs                                           | `docs/`                                                                                                   |
| Build/import/validation scripts                | `scripts/`                                                                                                |

The placeholder-scaffold root `assets/` tree and the orphaned `apps/web/src/features/` island named in older revisions of this table were deleted in a dead-code-removal pass — see `docs/migrations/DEAD-CODE-REMOVAL.md`.

There is also a **dormant, unread** JSON content pipeline under `content/campaigns/chronicle/units/unit-01/` (`campaign.json`, `unit.json`, `case.json`, `activities/*.json`, `assessments/*.json`) plus record templates in `content/library/`. `main.js` never imports from this tree (confirmed by import-graph trace). It represents a _fourth_ incompatible schema for the same Case 1.01 source content (alongside the live `unit-01-campaign.js` shape and two dead ones) — don't treat its presence as meaning it's wired up, and don't reconcile the schemas speculatively; that's tracked as future `ContentRegistry`/Zod work in `docs/architecture/PLATFORM-ARCHITECTURE-PROPOSAL.md`, not a current task.

### Author Mode and real Teacher Mode (Phase 22 — no longer a stub)

A development-only in-app panel (toggled via the chrome button, rendered by `authorPanel()` in `main.js`) lets a teacher edit two front-facing copy fields (unit title, central question) without touching layout, scoring, or progression logic — see `docs/decision-log/0003-author-mode-and-content-overrides.md` for the original intent. **This is real and working**, not a stub: edits persist via `apps/web/src/repositories/teacher-override-repository.js`, which falls back to a per-browser `local-teacher-override-store.js` for signed-out/local dev, or writes to a classroom-scoped `content_overrides` Supabase table once a real teacher/classroom is active (Phase 22). (An earlier revision of this file claimed the two content-edit inputs had no working event listener — that was fixed in an earlier phase and this file simply hadn't been updated; don't trust old staleness claims about this panel without checking `main.js` directly.)

Beyond Author Mode's content overrides, Chronicle now has real teacher-facing tooling: a teacher creates a classroom, provisions a student roster, reviews AI-evaluated submissions, and enters manual grades via the `teacher-dashboard`/`grading` screens (`main.js`) backed by a real, live Supabase project (accounts, classrooms, submissions, evaluations, manual grades — schema in `supabase/migrations/0001_init.sql`). The **Manage Content** editor (`main.js`, `manageContentCaseScreen()`, reached from the Teacher Dashboard's Units tab — `manageContentScreen()` was a separate standalone screen but was folded into that tab before Phase 28 and no longer exists as of Phase 37) lets a teacher browse every mission grouped by unit, see what kind of mission it is (walkable map vs. activity vs. Archive-Challenge-only), and swap a curated alternate for any of a mission's editable slots (source, any of the 4 quest types, or a Case 1.02 Exchange Ledger record) with a draft/preview/publish step, backed by `classroom_content_selections` (`supabase/migrations/0006_teacher_mode.sql`, generalized to all quest types by `0007_generalize_content_slots.sql` and to ledger records by `0010_ledger_record_slots.sql`). This is a real, bounded content-selection pipeline (pick from a small pre-authored pool per slot), **not** a from-scratch content-authoring tool — a teacher cannot write new question text/choices/answers through this screen; that remains a deferred future system. See `docs/architecture/session-reports/2026-07-18-real-teacher-mode-accounts-classrooms-grading.md` for the original design and `ARCHITECTURE-QUICKREF.md`'s Phase 22–24 and Phase 38 entries for current status — all migrations through `0010` are applied and live-verified as of Phase 38. ## Terminology

Fixed internal vocabulary — use these exact terms in code, copy, and UI strings. **Each entry below is the rule; `docs/reference/INVARIANTS.md` holds the full text, including the incident history that argues it. Read that entry before changing code in its area.**

- **Chronicle Institute** — the organization. **Institute Archive** — the visible hub room/screen name.
- **Entrance Hall** — the room the player arrives in. One of **three** hub rooms, all on the `institute` screen, told apart by `progress.currentHubRoom` (`"main"` | `"archive"` | `"hallway"`). There is no `intro-hallway` screen; **don't reintroduce a screen for a room.**
- **Chronotravel** — traveling to a historical setting (the `travel` screen).
- **Chronotravel plate** — the painted establishing shot a warp screen loads on. **Keyed by unit, not by case.** A plate's `note` is flavour and **must stay flavour** — never teach through it. A new unit costs one table line in `content/chronotravel-plates.js`.
- **Warp screen** — `travel` out and `return-warp` back, both built by `warpScreen()`. Full-bleed and chrome-less; three phases on one render, flipped via `data-warp-phase`. **A phase flip must never rebuild markup.** Second-beat timing is a CSS delay, not a class swap. The ring shows the dwell, not the bytes, and its `@property --warp-pct` **must declare `inherits: true`**. No tunnel canvas is emitted under `prefers-reduced-motion`. The screen never leaves on its own. Both recall paths play it.
- **Preservation Case** — the badge-case UI on the Archive trophy shelf. Styled like a Pokémon badge case, not a debug panel.
- **Navigation Table** — the Archive object the player walks to to pick a case/route.
- **Recall to Archive** — the field control returning the player to the Institute, landing beside the Navigation Table. **Two buttons, one action** (`field-recall`), but **only the beacon has a position** and is proximity-gated; the back link must never be gated. Anything repointing this must carry `exitPreviewIfActive()`. The beacon stays out of `nearestFieldInteraction()` deliberately.
- **Mission Tracker** — the field's objective panel. **One block**: a record row for the open mission takes that mission's name; an unopened record names the person carrying it. Don't reintroduce a name heading under the list.
- **Activity engine** — a playable interaction on the `activity` screen (`engine/activities/`). Four exist: `interview`, `assembly`, `discrepancy`, `trace`. **The engine key is registry key, screen id and `activityRoute` at once** — renaming one is a save-compatibility change. An engine holds **no APUSH facts**. Every authored field map has three missions; **read the slate off `THE-MAP-PROGRAM.md` §2's own table, never a prose summary**. **A unit must not repeat its neighbour's three engines**, and a repeated engine must be pointed at a different question. **An ASSEMBLY slot takes exactly one fragment** and every slot must be claimed. **Only a field case can host an activity.** **An activity states its own rules** — treat `howItWorks`/`terms`/`briefing` as defaults, not extras. **A record that is filed is filed**: every reducer refuses every verb that could un-complete it, and every renderer disables its own controls; INTERVIEW exempts `ask` and `log` only. `howItWorks` is a screen (Mission Instructions), not a panel — three steps, capped at four. An INTERVIEW's answer grid is **deliberately sparse**; `asked` and `logged` are different lists; `interviewTokens()` ids are **not unit-scoped**, so check new speaker ids against shipped ones. **Scope any new `.activity-shell`/`.activity-board` rule with `[data-activity-source]`.**
- **Mission** vs. **Archive Challenge** — load-bearing distinction. A mission is one case reached by Chronotravel, using the four swappable quest types. An Archive Challenge is a unit's extended written work (`saq`, `dbq`) from the Archive Terminal. Don't put a swappable type in `archiveChallenges[]` or an SAQ/DBQ in a case slot.
- **A finished quest renders as a record, and the record is sealed at both ends.** `renderQuest(type, quest, state, { readOnly: true })` — every renderer disables its own controls **and** `isSealedQuestTarget()` refuses in the four handlers, off `data-quest-readonly` on the quest root. Textareas go `readonly`, not `disabled`. There is no submit step in this codebase, so an editable finished quest re-grades itself. Applied to the completed mission only; the Archive Challenge and the Practice Check stay editable on purpose.
- **A mission has exactly one name** — the name half of `case.title` via `resolvedCaseName()`. The case number is an eyebrow, never inside a heading. `case.mechanic` is teacher-side help text. `case.shortTitle` means the _place_ and is not rename-aware.
- **Field interior** — a room a field map opens into, declared on `FIELD_MAPS[unitId].interiors`, told apart by `progress.currentFieldRoom`. **An interior declares exactly the fields an outdoor map declares** — that shape-equality is the design. Not a screen, not a portal graph, never nested. **A doorway is a column, not a gap** — a hole in an interior partition is only a door if the whole column above it is clear, and a room with interior walls is flood-filled after every furniture move.
- **A prop's size is the pack's opinion, not the world's.** Small props are drawn to fill their 48px tile; don't measure a new one against its neighbours. **Adding a sheet to a palette means adding its `import.meta.glob` in `main.js` too** — a missing one renders the whole map as an empty frame.
- **Hub object markers** are one class, `.hub-marker`, sized from each target's `marker` rect. Move an object in a generator, move its `marker` too. **Restyle `.hub-marker` in place; appending an override layer is how three competing styles came to exist.**
- Unit 1 badge areas: **Caribbean**, **Atlantic**, **Hispaniola** — all real, all playable in sequence.
- Institute NPCs: Director Rowan Hale, Dr. Amani Soto, Professor Julian Park — `director`, `amani`, `julian` in code.
- **Field Liaison** — Emery Voss, she/her. **The registry key is `liaison`, never the name.** Player-facing she is "Emery Voss" and **never her job title**. `progress.story.liaisonTrust` selects her line. She names Meridian in exactly one place, the `meridian-reveal` scene; Units 1–5 keep their field lines exactly as authored and only Unit 6 carries a `revealedText`. **Two costumes, one id** — `sheetFor()` is the single swap point. Nothing about the reveal is curricular.
- **A stationed body is furniture to the NPCs and a wall to the player.** Post new stations off the spawn's cardinals and out of corridors, then run `field-map-coordinates` and the field e2e specs.

## Gameplay invariants (regression-prone areas)

These recurred as bugs across many hotfix milestones. Be deliberate here and **re-test visually rather than trusting a syntax check.** As above, each line is the rule and `docs/reference/INVARIANTS.md` carries the case history — which is usually a record of the same bug shipping twice, and is the part that tells you which fix is the wrong one.

- **Camera must stay a pure function of player position.** No `scrollIntoView()`, no `.focus()`-triggered scrolling, no click-handler that moves the camera toward a clicked element.
- **Proximity-gated interaction.** Both `E` and click require the player already be in range — never teleport-and-interact.
- **One interaction prompt at a time**, cleared on close, on moving out of range, on screen change, and on reset. The field's `#fieldNotice` is a **status line, not a prompt**, and **an attempt that lands must clear the line left by one that missed**.
- **Dialogue renders anchored to the speaking NPC**, without resetting the world transform or scrolling the document. Content goes inside `.field-speech-bubble__scroll` or it will not scroll. **Check the cascade before the arithmetic here** — two rules in this area were dead for a full phase and were found by measuring in the browser, not by reading the file.
- **A per-frame path patches the DOM; it does not render.** Making the movement loop `render()` repaints map canvases mid-walk and turns a performance regression into four red specs. That used to be caught only by walks parking short — a signal that fires just as readily for a busy laptop, which is why Phase 93 gave the claim its own test: `tests/e2e/frame-budget.spec.js` counts wholesale `#app` re-renders during a walk and **does not care how fast the machine is**. Several specs failing at once in an untouched area is still one cause rather than several flakes; check the frame-budget spec first, because it names the cause.
- **NPC movement respects the same collision as the player**, and swaps sheets by facing direction. Four real directions, no mirroring, no `side` sheet. **The 48×56 canvas is pinned, not derived** — don't let a new character resize it.
- **An NPC has a job** — `station`, `route`, or `wander`, seeded per id.
  - **A route is authored as places, not waypoints.** Name the two or three places the person has business being; don't hand-write intermediate waypoints.
  - **Authoring cannot strand anyone** — stops snap, unpathable legs drop, an empty route degrades to a station.
  - **Two people must not share ground.** The coordinate test measures a route's whole walked path against 1.5 tiles, not its stops.
  - **A person and a piece of furniture must not share ground either.** Post staff two and a half tiles clear of an interactable object in a hub room; the seven field maps are swept at each target's own reach instead, and it is the **walked path** that catches this.
- **`E` and a click must reach the same thing the same way, and when they don't it is the keyboard that is wrong.** **When a control exists in two forms, the state changes live in one function both call** — `nearestInReach()`, and `openFieldRecord()`/`beginFieldRecord()`, are that shape. A record's availability is `sourceAvailability()`'s answer; **do not add a case-id literal beside it.** The dual is equally load-bearing: **when one variable answers two questions, the second question gets the first one's answer** — hence `codexOrigin` beside `sourceOrigin`.
- **A door is an interaction, and it competes for the same reach.** **Post a doorstep NPC two and a half tiles clear of the door**, or the room becomes unreachable — and **check the furniture as well as the cast**, which Phase 97 did not and Phase 98 paid for. Only `tests/e2e/suburb-interiors.spec.js` walks to a door from the street; every other interior's doorstep is still unguarded, so check a new one by hand.
  - **An interior must be attached after the `FIELD_MAPS` literal, not inside it** — a TDZ `ReferenceError` takes the app down on boot.
  - **A door's row comes off the generated `*_DOORS` export, never off the generator's constants by hand.**
  - **Every field surface must declare `isLand`**; interiors use `interiorGround(grid)`.
  - **A room smaller than its frame centres; it does not clamp.**
  - **A record draws only on its own surface; the checklist lists them all.** The Mission Tracker is deliberately the opposite and resolves across every surface.
- **Nothing in the game looks at where a character's name pill lands.** Any `base`-solidity object whose overlay row a character can stand on will draw over the label. There is no test and there should not be a clever one — look at the room.
- **A per-unit table with a sane fallback and no test is how a whole unit ships broken**, and it has now happened repeatedly. `FIELD_COPY`, `UNIT_MAP_VIEW` and `build-field-guide.js`'s four tables are all this shape; `tests/unit/field-map-coordinates.test.js` now asserts one entry per `FIELD_MAPS` key for each. **Add a new per-unit table to that test in the same commit that adds the table.**
- **A sequencing quest must be authored out of order** — keep each item's `position` right and its place in the array wrong. Enforced by `tests/unit/sequencing-quest-order.test.js`.
- **A scripted beat moves characters, never the screen.** `engine/cutscene.js` has **no camera command and never will**. One scripted-scene code path, not two. **A scene needing something the eight commands cannot say wants an `onDone`, not a ninth command.**
- **One input lock, `isHubInputLocked()`**, checked at the same three sites. Anything that locks movement must also suppress the interaction prompt. Keep the function even though it is one term.
- **Ground speed drives the walk cycle, per body, per moment.** If something moves a character at an unusual speed, it has to say so. **A second loop writing the same sprite is the same bug wearing a hat.**
- **A follower ends a walk a gap behind the leader, never on top of them.** Seed the trail from the follower's own position; `snapActor()` must read `command.follower`, not stale scene state.
  - **A stationed NPC is furniture to everyone else** — posts go into `createNavGrid`'s `occupied`.
- **The Director's intro dialogue box is a fixed three lines, and `.director-dialogue-box__text` is shared** with every hub scene. Scope the fixed height to `.director-scene`; leave the base rule alone. `overflow: hidden` truncates in silence, so the size is set against the longest authored line and guarded by `intro-sequence.spec.js`. **One custom property, one owner per breakpoint** — the narrow overrides use a closed range, not two open `max-width` queries.
- **The Director on the intro screens is a plate, not a walk sheet.** `DIRECTOR_CUTOUT` lives in `assets/plates/` behind a static string literal, is absent from `CHRONOTRAVEL_PLATES`, and carries **no `image-rendering: pixelated`** — the scene downscales it at a non-integer ratio. `CHARACTER_SHEETS.director` is still what the hub rooms draw.
- **The Codex reveal is a screen and owns the input while it is up.** Injected on demand, never an empty shell; the bar takes `inert`; the keydown branch checks for the veil before its Enter/Space advance. It fires after its line, from both places a line can finish.
- **Four numbers tie the cast to the world, and none of them should be eyeballed** — `--cast-h`, `--cast-foot` (each surface's collision foot-box centre), `--cast-label-top`, and a walk-cycle duration that comes from ground speed via `walkCycleSeconds()`, never a fixed value.

## Visual design language

- Palette (see CSS custom properties in `apps/web/src/styles/global.css`): deep navy (`--navy`), gold (`--gold`, `--gold-soft`), warm parchment/ink (`--paper`, `--ink`), muted teal accents. Keep new UI within this blue/gold/bronze/parchment historical-adventure look, not a generic admin-panel style.
- A custom bronze/gold ornate arrow cursor is already implemented as an inline SVG data URI in `global.css` — reuse/extend it rather than reverting to the system cursor for in-game surfaces.
- Don't cluster interactive elements together while leaving large map areas empty — placement should be diegetic (e.g. cartographer table near the ship, canoe worker near shore) and UI chrome (status panels, prompts) should sit outside the playable floor rather than overlapping NPCs, furniture, or pathways.

## Persistence

`chronicle-progress-store.js` (key `republic-builder.chronicle.unit-01.v2`) is still the base layer: a single flat `localStorage` blob, and the only save state for anyone not signed into a real classroom. **As of Phase 22, this is no longer the only copy for a signed-in student**: a real Supabase backend now exists (accounts, classrooms, submissions, evaluations, manual grades, classroom-scoped content overrides — schema in `supabase/migrations/0001_init.sql`), and `apps/web/src/repositories/progress-repository.js` layers background sync on top of the untouched local store — exactly the "small service/adapter in front of a versioned save schema" this section used to describe as future design intent. When adding new persisted fields, still extend `DEFAULT_PROGRESS` and the merge logic in `readProgress()` — that pattern is unchanged, just now also mirrored to `student_world_profiles` in Supabase. See `docs/architecture/session-reports/2026-07-18-real-teacher-mode-accounts-classrooms-grading.md` for the full design and what's still unverified against a live project.

## Development workflow expectations

- Prefer small, focused changes over broad refactors; don't fix unrelated things in the same pass.
- Avoid modifying `vite.config.js` unless the task genuinely requires it.
- Compilation/syntax passing is not sufficient to call something fixed — this is a visual/interactive game. Verify using the ladder below before considering a change done. Don't commit until the requested behavior has actually been tested.
- **No `/verify` skill exists in this repo** — an earlier revision of this file referenced one; don't look for it or invent an ad hoc equivalent. The verification ladder below is the actual expectation.

### Verification ladder (cheapest first — escalate only as needed)

Run the cheapest check that actually exercises what you changed; stop once you've cleared the tier that matters for this change. Don't jump straight to a manual/MCP browser pass by default — it is the _most_ expensive tier, not the default one.

1. **Targeted `vitest`**, scoped to the changed file/pattern: `npx vitest run tests/unit/<file>.test.js`, not a bare `npm run test`.
2. **`npm run validate:content`** — only if content files changed (schemas, `unit-0N-campaign.js`, `content/quests/*`).
3. **`npm run test:e2e`** — the real, committed Playwright suite (`tests/e2e/*.spec.js`, added Phase 29; `npm run docs:stats` for current counts). This is the default way to verify a player-visible interaction — run it before reaching for a manual browser pass, not after. For a CSS-only change, run `npm run test:e2e -- visual-regression` specifically: it screenshots every gameplay screen at 1366×768 against the committed win32 baselines and will show you a pixel diff if anything moved. **It is not a check on cast art** — every screenshot containing a character hides `.hub-npc`/`[data-npc]` first, because NPCs animate on a rAF loop and are never pixel-stable, so a new or re-drawn sprite moves nothing here and must be verified by `character-sheet-geometry.test.js` and by eye. **Review a changed baseline before accepting it** — open the `-diff.png` and confirm every difference is one you intended; a blind `--update-snapshots` turns the whole suite into a rubber stamp.
4. **Full `npm run test` / `npm run lint` / `npm run build`** — at milestone boundaries or when the change touches shared infrastructure (a screen-routing guard, a repository facade, a quest-type contract all four types implement).
5. **A manual browser pass (`npm run dev`, by hand or via an MCP browser tool)** — only for an interaction genuinely uncovered by any committed spec. When you do this, **bank it**: add the scenario as a new `tests/e2e/*.spec.js` file (or a case in an existing one) so the next session doesn't re-derive it by hand. A manual pass that isn't banked is cost paid twice for the same coverage.

### The Spine Review — the standing part-by-part playtest program

`docs/playtest/PLAYTHROUGH-LEDGER.md` is the single source of program state: an ordered walk of the **student** experience, intro through unit completion, in thirteen parts. Read the ledger before starting a review part or acting on a defect report about a player-facing screen — a finding may already be recorded and routed. Each part gets its own `part-NN-*.md` **when it starts**, never before; the ledger holds status and counts and never finding text. The protocol and the severity/category taxonomy live in the ledger, in one place, deliberately.

**Parts 0 through 9 are closed as of Phase 90H**, which is the whole of the strictly-ordered spine; 10, 11 and 12 branch off it and are reorderable, so the program no longer names its own next row. Two rules from it that bind any session touching the program: **an S3 finding must name a destination** (a part number, the content queue, or an ADR), and **a part's ledger row is updated in the same commit as its fix** — if the row isn't in the diff, the part isn't closed. The program fixes behaviour, never shape: no restructuring, no new systems, no new content. Teacher surfaces are deliberately out of scope.

`?warp=<name>` (dev only, `DEV_WARPS` in `main.js`) boots straight into a named save state so a review pass starts where it starts — `intro`, `hall`, `hub`, `table`, `field`, `mission`, `railhead`, `port`, `reveal`. It is gated on `import.meta.env.DEV` and verified absent from production builds; adding a state is one line in that table. **`window.__chronicleNav` is the other dev-only surface, gated the same way** (Phase 94): it samples `isFieldBlocked`/`isHubBlocked` across the active grid so the e2e walker can breadth-first a route through the room's real collision instead of sliding along walls. A test helper may read the game's state; it must not restate the game's rules — see `docs/decision-log/0093-the-walker-was-blind.md`.
